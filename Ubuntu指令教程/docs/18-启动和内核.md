## 249 ★&nbsp;&nbsp;update-initramfs：重建 initramfs

> 级别：★ 高级 · 软件包：`dracut`（Ubuntu 26.04 默认由 dracut 提供此命令）

### 1. 作用

开机时，内核先加载一个小型的临时根文件系统 initramfs，里面有挂载真正根分区所需的驱动和工具（磁盘控制器驱动、LVM、RAID、磁盘解密）。真正的根分区挂好后再切换过去。

修改了这些和“启动时挂载根分区”相关的配置之后，要重建 initramfs，否则下次开机可能找不到根分区：

- 修改了 `/etc/crypttab`（磁盘加密）、`/etc/mdadm/mdadm.conf`（RAID）；
- 安装了需要在启动早期加载的驱动；
- 修改了内核模块的黑名单。

`update-initramfs` 用来重建。

### 2. 基本格式

```bash
sudo update-initramfs -u                # 更新当前内核的 initramfs
sudo update-initramfs -u -k all         # 更新所有已安装内核的
sudo update-initramfs -c -k 内核版本    # 为某个内核新建
```

文件生成在 `/boot/initrd.img-内核版本`。

### 3. Ubuntu 26.04 的变化

从 Ubuntu 25.10 开始，默认用 **dracut** 生成 initramfs，取代了以前的 initramfs-tools。为了兼容，`update-initramfs` 命令仍然保留，由 dracut 包提供：

```
$ dpkg -S /usr/sbin/update-initramfs
dracut: /usr/sbin/update-initramfs

$ apt-cache policy initramfs-tools dracut | grep -E "^[a-z]|Installed"
initramfs-tools:
  Installed: (none)
dracut:
  Installed: 110-11ubuntu0.1

$ update-initramfs
You must specify at least one of -c, -u, or -d.
...
```

所以网上针对旧版本的教程里，修改 `/etc/initramfs-tools/` 下的配置在 26.04 上不起作用；dracut 的配置放在 `/etc/dracut.conf.d/`。

> ⚠️ 实际生成 initramfs 未实机验证（测试环境没有安装 Ubuntu 内核）。“从 25.10 开始”的版本信息未经实测核对，以本机 `dpkg -S /usr/sbin/update-initramfs` 的结果为准。

### 4. ⚠️ 踩坑警告

| 现象 | 原因 | 怎么改 |
|---|---|---|
| 改了 RAID 或加密配置后重启，停在 `(initramfs)` 提示符，找不到根分区 | 没有重建 initramfs | 用救援盘启动，chroot 进系统执行 `update-initramfs -u`；或者在 GRUB 菜单里选旧内核启动后再修 |
| /boot 分区满了，重建失败 | 旧内核和旧 initramfs 太多 | `sudo apt autoremove` 删除旧内核 |

### 5. 一句话总结

改了 RAID、加密、早期驱动之后，执行 `sudo update-initramfs -u`。

## 250 ★&nbsp;&nbsp;update-grub：更新 GRUB 引导菜单

> 级别：★ 高级 · 软件包：`grub2-common`

### 1. 作用

GRUB 是开机时第一个运行的程序，显示启动菜单、加载内核。它的菜单配置 `/boot/grub/grub.cfg` 是**自动生成的**，不要手改。你修改的是 `/etc/default/grub`（启动参数、默认项、等待时间），改完执行 `update-grub` 重新生成。

`update-grub` 实际上就是一个调用 grub-mkconfig 的小脚本：

```
$ cat /usr/sbin/update-grub
#!/bin/sh
set -e
exec grub-mkconfig -o /boot/grub/grub.cfg "$@"
```

### 2. 常改的配置项（/etc/default/grub）

| 配置项 | 作用 |
|---|---|
| `GRUB_DEFAULT=0` | 默认启动第几项；`saved` 表示记住上次的选择 |
| `GRUB_TIMEOUT=5` | 菜单等待几秒 |
| `GRUB_TIMEOUT_STYLE=menu` | 显示菜单（默认 hidden 时不显示，开机按住 Shift 或 Esc 才出现） |
| `GRUB_CMDLINE_LINUX_DEFAULT="quiet splash"` | 传给内核的参数 |
| `GRUB_CMDLINE_LINUX=""` | 每一项（包括恢复模式）都加的内核参数 |

### 3. 常用示例

给内核加参数（例如 kdump 需要的 crashkernel）：

```bash
sudo nano /etc/default/grub
# 改成：GRUB_CMDLINE_LINUX_DEFAULT="quiet splash crashkernel=512M"
sudo update-grub
sudo reboot
cat /proc/cmdline          # 重启后确认参数生效
```

服务器上让启动菜单总是显示，方便出问题时选择旧内核：

```
GRUB_TIMEOUT_STYLE=menu
GRUB_TIMEOUT=5
```

> ⚠️ 本页未实机验证：测试环境没有 /boot 和 GRUB 安装。

### 4. ⚠️ 踩坑警告

| 现象 | 原因 | 怎么改 |
|---|---|---|
| 直接改了 /boot/grub/grub.cfg，下次更新内核后改动消失 | 这个文件每次都会重新生成 | 改 /etc/default/grub 或 /etc/grub.d/ 下的脚本 |
| 内核参数写错，开不了机 | 参数被直接传给了内核 | 开机时在 GRUB 菜单按 `e` 临时删掉错误的参数，`Ctrl+X` 启动，进系统后再改回 |

### 5. 一句话总结

改 /etc/default/grub，然后 `sudo update-grub`，不要手改 grub.cfg。

## 251 ★&nbsp;&nbsp;grub-install：把 GRUB 安装到磁盘

> 级别：★ 高级 · 软件包：`grub2-common`，配合 `grub-efi-amd64`（UEFI）或 `grub-pc`（传统 BIOS）

### 1. 作用

`grub-install` 把 GRUB 引导程序本身安装到磁盘上：UEFI 系统装到 EFI 分区，传统 BIOS 系统写入磁盘开头的 MBR。平时不需要它；只有在**引导程序损坏、开机直接进不了 GRUB**的时候（换了系统盘、装 Windows 覆盖了引导、EFI 分区被误删）才用它修复，通常在救援模式下 chroot 进系统后执行。

### 2. 基本格式

```bash
sudo grub-install                     # UEFI：自动装到 /boot/efi
sudo grub-install /dev/sda            # 传统 BIOS：写到整块盘（不是分区）
```

| 参数 | 作用 |
|---|---|
| `--target=x86_64-efi` / `i386-pc` | 指定 UEFI 或 BIOS |
| `--efi-directory=/boot/efi` | EFI 分区的挂载位置 |
| `--bootloader-id=ubuntu` | UEFI 启动项的名称 |

### 3. 常用示例

从 Ubuntu 安装盘启动后修复引导（UEFI 系统）：

```bash
sudo mount /dev/sda2 /mnt
sudo mount /dev/sda1 /mnt/boot/efi
for d in dev proc sys run; do sudo mount --rbind /$d /mnt/$d; done
sudo chroot /mnt
grub-install
update-grub
exit
sudo reboot
```

判断是 UEFI 还是 BIOS：`[ -d /sys/firmware/efi ] && echo UEFI || echo BIOS`。

> ⚠️ 本页未实机验证：测试环境没有可供安装引导程序的磁盘。

### 4. ⚠️ 踩坑警告

| 现象 | 原因 | 怎么改 |
|---|---|---|
| BIOS 系统上写成了 `grub-install /dev/sda1` | 引导程序要写到整块盘 | 写 `/dev/sda` |
| UEFI 系统上报 `cannot find EFI directory` | EFI 分区没有挂载到 /boot/efi | 先挂载，或用 `--efi-directory` 指定 |

### 5. 一句话总结

开机进不了 GRUB 时，救援模式 chroot 后 `grub-install` + `update-grub`。

## 252 ★&nbsp;&nbsp;dkms：自动重新编译第三方内核模块

> 级别：★ 高级 · 软件包：`dkms`（3.2.2）

### 1. 作用

NVIDIA 显卡驱动、VirtualBox、部分网卡和 RAID 卡的厂商驱动，是不在 Ubuntu 内核里的第三方内核模块。内核模块必须针对**具体的内核版本**编译，每次内核升级都要重新编译一遍。DKMS（Dynamic Kernel Module Support）做的就是这件事：内核升级时自动为新内核重新编译这些模块。

`dkms` 命令主要用来查看状态，出问题时手动重新编译。

### 2. 常用命令

| 命令 | 作用 |
|---|---|
| `dkms status` | 列出 DKMS 管理的模块，以及为哪些内核编译过 |
| `sudo dkms autoinstall` | 为当前内核编译所有缺少的模块 |
| `sudo dkms install 模块/版本 -k 内核版本` | 为指定内核编译安装 |
| `sudo dkms remove 模块/版本 --all` | 删除 |

### 3. 常用示例

```
$ dkms --version
dkms-3.2.2

$ dkms status
```

没有第三方模块时输出为空。装了 NVIDIA 驱动的机器上，会显示类似 `nvidia/570.xx, 6.x.x-xx-generic, x86_64: installed` 的行，每个内核一行。

内核升级后显卡驱动失效：

```bash
dkms status                        # 看新内核那一行是不是 installed
sudo apt install linux-headers-$(uname -r)   # DKMS 编译需要内核头文件
sudo dkms autoinstall
sudo reboot
```

> ⚠️ 带模块时的输出和修复步骤未实机验证。

### 4. 一句话总结

升级内核后驱动没了，先 `dkms status`，再装 headers 后 `dkms autoinstall`。

## 253 ★&nbsp;&nbsp;mokutil：管理安全启动密钥

> 级别：★ 高级 · 软件包：`mokutil`（0.7.2）

### 1. 作用

UEFI 安全启动（Secure Boot）只允许加载经过签名的引导程序和内核模块，防止恶意软件在开机阶段植入。Ubuntu 自带的内核和驱动都有签名；但通过 DKMS 编译的第三方模块（如 NVIDIA 驱动）是在你的机器上现场编译的，没有官方签名。

解决办法是用 MOK（Machine Owner Key，机器所有者密钥）：在本机生成一个密钥给这些模块签名，再把这个密钥注册进固件。`mokutil` 管理 MOK 的注册，也能查看安全启动是否开启。

### 2. 常用命令

| 命令 | 作用 |
|---|---|
| `mokutil --sb-state` | 安全启动是否开启 |
| `mokutil --list-enrolled` | 已注册的密钥 |
| `sudo mokutil --import 公钥.der` | 申请注册一个密钥（设置一次性密码） |
| `mokutil --list-new` | 等待注册的密钥 |

### 3. 注册流程

```bash
mokutil --sb-state
# SecureBoot enabled
sudo mokutil --import /var/lib/shim-signed/mok/MOK.der   # 设置一个临时密码
sudo reboot
```

重启时会出现蓝色的 MOK 管理界面：选择 **Enroll MOK** → **Continue** → **Yes**，输入刚才设置的临时密码，再选择重启。之后签名的模块就能正常加载了。用 ubuntu-drivers 安装 NVIDIA 驱动时，安装程序会自动走这个流程。

测试环境是没有 UEFI 变量的虚拟机：

```
$ mokutil --sb-state
EFI variables are not supported on this system
```

> ⚠️ 注册流程未实机验证。

### 4. ⚠️ 踩坑警告

| 现象 | 原因 | 怎么改 |
|---|---|---|
| 重启时蓝色界面一闪而过，没来得及操作，密钥没注册上 | 界面有等待时间 | 重新执行 `mokutil --import`，重启时注意屏幕，按任意键进入 |
| 驱动装好后 `modprobe` 报 `Key was rejected by service` | 模块的签名密钥没有注册 | 按上面的流程注册 MOK |

### 5. 一句话总结

开着安全启动装第三方驱动：`mokutil --import`，重启时在蓝色界面完成注册。

## 254 ★&nbsp;&nbsp;efibootmgr：管理 UEFI 启动项

> 级别：★ 高级 · 软件包：`efibootmgr`（18）

### 1. 作用

UEFI 固件里保存着一份启动项列表（Ubuntu、Windows Boot Manager、U 盘、网络启动），以及它们的启动顺序。`efibootmgr` 在 Linux 里直接查看和修改这份列表，不用进 BIOS 设置界面。双系统机器开机总是进 Windows、换盘后启动项残留，都用它处理。

### 2. 常用命令

| 命令 | 作用 |
|---|---|
| `efibootmgr` | 列出启动项和启动顺序 |
| `efibootmgr -v` | 同时显示每项对应的分区和文件 |
| `sudo efibootmgr -o 0001,0000` | 修改启动顺序 |
| `sudo efibootmgr -n 0002` | 只有下一次启动时从 0002 启动 |
| `sudo efibootmgr -b 0003 -B` | 删除 0003 这一项 |

### 3. 常用示例

```bash
efibootmgr
```

输出类似：

```
BootCurrent: 0001
BootOrder: 0001,0000,0002
Boot0000* Windows Boot Manager
Boot0001* ubuntu
Boot0002* UEFI: USB Disk
```

`BootCurrent` 是这次从哪项启动的，`BootOrder` 是启动顺序。要让 Ubuntu 优先：`sudo efibootmgr -o 0001,0000,0002`。

> ⚠️ 上面的输出是格式示意，未实机验证：测试环境不是 UEFI 系统，efibootmgr 报 `EFI variables are not supported on this system.`。

### 4. 一句话总结

UEFI 启动顺序不对，`efibootmgr` 看编号，`-o` 调整顺序。

## 275 ★&nbsp;&nbsp;cloud-init：云主机首次启动时自动初始化

> 级别：★ 高级 · 软件包：`cloud-init`（26.2）

### 1. 作用

在阿里云、腾讯云、AWS 上新建一台 Ubuntu 云主机，它开机后自动设好了主机名、建好了用户、放好了你的 ssh 公钥，这些都是 cloud-init 做的。创建云主机时可以填写一段 “user-data”（用户数据），cloud-init 在**第一次开机**时按它执行：装软件、写配置文件、执行命令。multipass、LXD、Proxmox 也支持 cloud-init。

把初始化步骤写成 cloud-init 配置，每台新服务器开出来就是配好的，不用登录后一台台手动操作。

### 2. 常用命令

| 命令 | 作用 |
|---|---|
| `cloud-init status --wait` | 等待初始化完成并显示结果（done / error） |
| `cloud-init schema -c 文件` | 检查配置文件的格式 |
| `cloud-init query userdata` | 查看这台机器收到的 user-data |
| `sudo cloud-init clean --logs` | 清除状态，下次开机重新执行一遍（制作镜像前用） |

日志在 `/var/log/cloud-init.log` 和 `/var/log/cloud-init-output.log`（命令的输出）。

### 3. 配置示例

```yaml
#cloud-config
hostname: web01
timezone: Asia/Shanghai
packages:
  - nginx
users:
  - name: deploy
    groups: sudo
    shell: /bin/bash
    ssh_authorized_keys:
      - ssh-ed25519 AAAA... deploy@example
runcmd:
  - systemctl enable --now nginx
```

第一行 `#cloud-config` 不能省。先检查格式：

```
$ cloud-init schema -c user-data.yaml
Valid schema user-data.yaml
```

写错了一个键名（`package` 少了 s）：

```
$ cloud-init schema -c bad.yaml
Error: Cloud config schema errors: package: Additional properties are not allowed ('package' was unexpected)

Error: Invalid schema: user-data
```

在 multipass 上试：`multipass launch 26.04 -n web01 --cloud-init user-data.yaml`。

> ⚠️ 实际的首次启动初始化未实机验证；schema 检查为实测。

### 4. ⚠️ 踩坑警告

| 现象 | 原因 | 怎么改 |
|---|---|---|
| 改了 user-data 后重启，没有任何变化 | cloud-init 的大部分模块只在第一次开机时执行 | 新建一台验证；或在测试机上 `cloud-init clean` 后重启 |
| 用自己做的镜像开出的新机器，ssh 主机密钥、机器 ID 全都一样 | 制作镜像前没清理 | 制作镜像前执行 `sudo cloud-init clean --logs --machine-id` |

### 5. 一句话总结

新服务器的初始化写成 `#cloud-config`，先 `cloud-init schema -c` 检查，开机后看 `status --wait`。

## 299 ★&nbsp;&nbsp;kdump-config：配置内核崩溃转储

> 级别：★ 高级 · 软件包：`kdump-tools`

### 1. 作用

用户程序崩溃留下的是 core 文件；**内核本身**崩溃（kernel panic）时，机器直接死机或重启，什么都没留下，事后很难查原因。kdump 预先在内存里保留一小块空间，加载一个备用的小内核；主内核崩溃时，备用内核接管，把崩溃时的内存保存到 `/var/crash/`，之后可以用 crash 工具分析，或者交给 Canonical 等厂商的支持人员。

`kdump-config` 查看和管理 kdump 的状态。

### 2. 常用命令

| 命令 | 作用 |
|---|---|
| `kdump-config show` | 当前配置和是否就绪 |
| `kdump-config status` | 是否已加载备用内核 |
| `sudo kdump-config load` / `unload` | 加载 / 卸载备用内核 |

### 3. 启用步骤

```bash
sudo apt install kdump-tools          # 安装时会询问是否启用，选 Yes
grep USE_KDUMP /etc/default/kdump-tools   # 应为 USE_KDUMP=1
```

还需要给内核加 `crashkernel=` 参数预留内存（见 [update-grub](#cmd-update-grub)），安装程序一般会自动添加，重启后生效。

```
$ kdump-config show
 * no crashkernel= parameter in the kernel cmdline
DUMP_MODE:		kdump
USE_KDUMP:		1
KDUMP_COREDIR:		/var/crash
crashkernel addr:
   /var/lib/kdump/vmlinuz
...
```

测试环境的内核没有 crashkernel 参数，所以第一行提示还没有就绪。配置正确并重启后，`kdump-config status` 会显示 `current state: ready to kdump`。

> ⚠️ 加载和实际转储未实机验证。

### 4. 一句话总结

服务器莫名死机重启，就启用 kdump：装 kdump-tools、加 crashkernel、`kdump-config show` 确认 ready。
