## 128 ★★&nbsp;&nbsp;git：版本控制

> 级别：★★ 中级 · 软件包：`git`（2.53.0）

### 1. 作用

`git` 记录文件的每一次修改：谁、什么时候、改了什么、为什么改。改坏了可以回到任何一个历史版本；多人可以在不同分支上各自开发，再合并到一起；和 GitHub、GitLab 等远程仓库同步，就是代码的备份和协作中心。

除了代码，服务器的配置文件（nginx、应用配置）、运维脚本、文档也适合用 git 管理。

git 的子命令非常多，这里只讲日常最常用的一组。

### 2. 基本概念

| 概念 | 含义 |
|---|---|
| 仓库（repository） | 一个被 git 管理的目录，历史记录保存在其中的 `.git` 子目录里 |
| 工作区 | 你正在编辑的文件 |
| 暂存区（staging） | 用 `git add` 挑出来、准备下一次提交的修改 |
| 提交（commit） | 一次保存的快照，带说明和一个唯一编号 |
| 分支（branch） | 一条独立的修改线，默认分支叫 main |
| 远程（remote） | 另一台机器上的仓库，通常叫 origin |

### 3. 常用子命令

| 子命令 | 作用 |
|---|---|
| `config --global user.name / user.email` | 设置提交者的名字和邮箱（只需设置一次） |
| `init 目录` | 新建仓库 |
| `clone 地址` | 复制一个远程仓库到本地 |
| `status` | 哪些文件改了、哪些已暂存 |
| `add 文件` / `add .` | 加入暂存区 |
| `commit -m "说明"` | 提交 |
| `commit -am "说明"` | 把已跟踪文件的修改直接提交（跳过 add） |
| `diff` | 看还没暂存的修改 |
| `log --oneline` | 简洁的历史 |
| `switch -c 分支` / `switch 分支` | 新建并切换 / 切换分支 |
| `merge 分支` | 合并分支 |
| `restore 文件` | 放弃工作区的修改 |
| `pull` / `push` | 从远程拉取 / 推送到远程 |
| `tag 名称` | 给当前提交打标签（如版本号） |

### 4. 常用示例

#### 4.1 第一次使用

```
$ git config --global user.name "Tom"
$ git config --global user.email "tom@example.com"
$ git config --global init.defaultBranch main
$ git config --global --list
user.name=Tom
user.email=tom@example.com
init.defaultbranch=main
```

#### 4.2 新建仓库并第一次提交

```
$ git init price-app
Initialized empty Git repository in /home/tom/demo/price-app/.git/

$ cd price-app; cp ../src/products.csv .; printf 'logs/\n*.log\n' > .gitignore

$ git status
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	.gitignore
	products.csv

nothing added to commit but untracked files present (use "git add" to track)

$ git add .; git status --short
A  .gitignore
A  products.csv

$ git commit -m "初始化：产品价格表"
[main (root-commit) 2a27870] 初始化：产品价格表
 2 files changed, 8 insertions(+)
 create mode 100644 .gitignore
 create mode 100644 products.csv
```

`.gitignore` 里写的文件（日志目录、`*.log`）不会被 git 管理。

#### 4.3 修改、查看差异、提交

```
$ sed -i 's/,35$/,38/' products.csv; git status --short
 M products.csv

$ git diff
diff --git a/products.csv b/products.csv
index da7ced1..0c490f0 100644
--- a/products.csv
+++ b/products.csv
@@ -2,5 +2,5 @@ code,name,category,price
 U001,探头A,探头,12000
 U002,探头B,探头,15000
 U003,主机X,主机,280000
-U004,凝胶,耗材,35
+U004,凝胶,耗材,38
 U005,探头A,探头,12000

$ git commit -am "凝胶价格调整为 38"
[main ff1aa75] 凝胶价格调整为 38
 1 file changed, 1 insertion(+), 1 deletion(-)

$ git log --oneline
ff1aa75 凝胶价格调整为 38
2a27870 初始化：产品价格表
```

`git status --short` 里，`M` 是已修改，`A` 是新增，`??` 是未跟踪。

#### 4.4 分支和合并

```
$ git switch -c feature/new-product
Switched to a new branch 'feature/new-product'

$ echo "U006,新品,耗材,99" >> products.csv; git commit -qam "新增 U006"; git branch
* feature/new-product
  main

$ git switch main; git merge feature/new-product
Switched to branch 'main'
Updating ff1aa75..3050125
Fast-forward
 products.csv | 1 +
 1 file changed, 1 insertion(+)

$ git log --oneline --graph
* 3050125 新增 U006
* ff1aa75 凝胶价格调整为 38
* 2a27870 初始化：产品价格表
```

`Fast-forward` 表示 main 在这期间没有新提交，直接把 main 移动到分支的最新位置即可。

#### 4.5 放弃修改

```bash
git restore products.csv            # 放弃工作区里还没 add 的修改
git restore --staged products.csv   # 撤销 add，修改仍保留在工作区
```

#### 4.6 远程仓库

```bash
git clone https://github.com/用户/仓库.git
git remote add origin https://github.com/用户/仓库.git
git push -u origin main
git pull
```

### 5. ⚠️ 踩坑警告

| 现象 | 原因 | 怎么改 |
|---|---|---|
| 提交时报 `Please tell me who you are` | 没设置 user.name 和 user.email | 按 4.1 设置 |
| push 时报 `could not read Username for 'https://github.com'`，或者输入密码后被拒绝 | GitHub 等平台不再接受账号密码推送 | 用 ssh 地址（`git@github.com:用户/仓库.git`）配合 ssh 密钥，或使用平台生成的访问令牌 |
| 把密码、密钥文件提交进了仓库 | 没写 .gitignore | 立即更换密码；从历史中清除需要专门的工具，提交前养成看 `git status` 的习惯 |
| `git pull` 报 `Your local changes would be overwritten` | 本地有未提交的修改，和远程的修改冲突 | 先 commit，或用 `git stash` 暂存，pull 后再 `git stash pop` |
| `git commit` 后显示 `no changes added to commit` | 修改还没有 add | 先 `git add`，或用 `commit -am` |

### 6. 一句话总结

`git status` 看状态，`add` + `commit -m` 保存，`switch -c` 开分支，`push`/`pull` 同步。

## 129 ★★&nbsp;&nbsp;docker：容器管理

> 级别：★★ 中级 · 软件包：`docker.io`（Ubuntu 软件源）或 Docker 官方的 `docker-ce`

### 1. 作用

`docker` 把应用和它需要的运行环境（系统库、语言运行时、配置）打包成**镜像**，再从镜像启动一个隔离运行的**容器**。同一个镜像在开发机、测试机、生产服务器上运行结果一致，部署时不再需要在每台机器上装一遍 JDK、Node、Python。

| 概念 | 含义 |
|---|---|
| 镜像（image） | 只读的模板，如 `nginx:1.27`、`mysql:8.4` |
| 容器（container） | 从镜像启动的运行实例，可以有多个 |
| 仓库（registry） | 存放镜像的地方，默认是 Docker Hub |
| 卷（volume） | 容器外部的持久存储，容器删除后数据仍在 |

### 2. 安装

```bash
sudo apt install docker.io            # Ubuntu 软件源里的版本
sudo usermod -aG docker $USER         # 加入 docker 组后，不用 sudo 也能执行 docker
# 重新登录后生效
```

也可以按 Docker 官方文档安装 `docker-ce`，版本更新。

### 3. 常用子命令

| 子命令 | 作用 |
|---|---|
| `run [参数] 镜像` | 启动一个新容器 |
| `ps` / `ps -a` | 运行中的容器 / 全部容器 |
| `images` | 本地的镜像 |
| `pull 镜像` | 下载镜像 |
| `logs [-f] 容器` | 查看容器输出 |
| `exec -it 容器 bash` | 进入运行中的容器执行命令 |
| `stop` / `start` / `restart 容器` | 停止 / 启动 / 重启 |
| `rm 容器` / `rmi 镜像` | 删除容器 / 镜像 |
| `build -t 名称 .` | 用当前目录的 Dockerfile 构建镜像 |

`run` 的常用参数：

| 参数 | 作用 |
|---|---|
| `-d` | 后台运行 |
| `--name 名字` | 给容器起名 |
| `-p 主机端口:容器端口` | 端口映射 |
| `-v 主机目录:容器目录` | 挂载目录，数据保存在主机上 |
| `-e 变量=值` | 环境变量 |
| `--restart unless-stopped` | 容器退出或主机重启后自动启动 |

### 4. 常用示例

```bash
docker run -d --name web -p 8080:80 nginx:1.27
docker ps
docker logs -f web
docker exec -it web bash
docker stop web && docker rm web
```

启动一个数据持久化的 MySQL：

```bash
docker run -d --name db \
  -e MYSQL_ROOT_PASSWORD='Db@2026' \
  -v /srv/mysql:/var/lib/mysql \
  -p 127.0.0.1:3306:3306 \
  --restart unless-stopped \
  mysql:8.4
```

`127.0.0.1:3306:3306` 表示只允许本机访问数据库端口。

> ⚠️ 本页未实机验证：测试环境里不能运行 Docker 守护进程。命令写法为 Docker 长期稳定的用法，镜像版本号仅为示例。多容器编排（docker compose）在高级篇讲。

### 5. ⚠️ 踩坑警告

| 现象 | 原因 | 怎么改 |
|---|---|---|
| `permission denied while trying to connect to the Docker daemon socket` | 当前用户不在 docker 组 | `sudo usermod -aG docker $USER` 后重新登录 |
| 删掉容器后，数据库数据全没了 | 数据存在容器内部 | 用 `-v` 把数据目录挂载到主机 |
| `-p 3306:3306` 映射的端口，ufw 拦不住，外网能直接访问 | Docker 直接修改 iptables，绕过 ufw | 绑定到 127.0.0.1，或用云安全组控制 |
| 磁盘被 Docker 占满 | 旧镜像、停止的容器、构建缓存越积越多 | `docker system df` 查看，`docker system prune` 清理 |
| 容器里的时间差 8 小时 | 镜像默认用 UTC | `-e TZ=Asia/Shanghai` |

### 6. 一句话总结

`docker run -d --name 名字 -p 端口 -v 目录 镜像` 启动，数据一定挂载到主机。

## 204 ★&nbsp;&nbsp;strace：跟踪系统调用

> 级别：★ 高级 · 软件包：`strace`（6.19）

### 1. 作用

程序要读文件、连网络、启动子进程，都必须通过系统调用请内核去做。`strace` 把一个程序发出的每一个系统调用、参数和返回结果都打印出来。程序报错信息含糊（“配置加载失败”）、卡住不动、启动就退出时，strace 能直接看到它最后在找哪个文件、连哪个地址、卡在哪个调用上。

### 2. 基本格式

```bash
strace [参数] 命令           # 启动并跟踪
sudo strace -p PID           # 跟踪已经在运行的进程
```

### 3. 常用参数

| 参数 | 作用 |
|---|---|
| `-e trace=类型` | 只看某类调用：`openat`、`file`、`network`、`process`、`connect` |
| `-f` | 同时跟踪子进程 |
| `-c` | 不逐条打印，最后输出各类调用的次数和耗时统计 |
| `-o 文件` | 输出写入文件 |
| `-tt` | 每行带精确到微秒的时间 |
| `-T` | 显示每个调用花了多长时间 |
| `-s 长度` | 字符串显示的长度，默认 32 |

### 4. 常用示例

#### 4.1 程序到底打开了哪些文件

```
$ strace -e trace=openat cat readme.txt
...
openat(AT_FDCWD, "/usr/share/coreutils/locales/cat/en-US.ftl", O_RDONLY|O_CLOEXEC) = -1 ENOENT (No such file or directory)
openat(AT_FDCWD, "readme.txt", O_RDONLY|O_CLOEXEC) = 4
hello
+++ exited with 0 +++
```

`= 4` 表示成功，返回文件描述符 4；`= -1 ENOENT` 表示文件不存在。程序报“找不到配置”时，搜输出里的 `ENOENT`，就知道它实际去哪里找了。

#### 4.2 子进程执行了什么

```
$ strace -f -e trace=execve bash -c 'ls >/dev/null; date >/dev/null'
execve("/usr/bin/bash", ["bash", "-c", "ls >/dev/null; date >/dev/null"], 0x7ffcdbdd5b78 /* 12 vars */) = 0
[pid    48] execve("/usr/bin/ls", ["ls"], 0x55caccbf5a20 /* 12 vars */) = 0
[pid    49] execve("/usr/bin/date", ["date"], 0x55caccbf5a20 /* 12 vars */) = 0
```

排查“这个安装脚本到底调用了哪些命令”很方便。

#### 4.3 连到了哪个地址

```
$ strace -e trace=connect curl -s -m 2 http://127.0.0.1:9
...
connect(5, {sa_family=AF_INET, sin_port=htons(9), sin_addr=inet_addr("127.0.0.1")}, 16) = -1 EINPROGRESS (Operation now in progress)
```

#### 4.4 统计

```
$ strace -c ls > /dev/null
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ------------------
  0.00    0.000000           0        17           read
  0.00    0.000000           0         1           write
  0.00    0.000000           0        12           close
...
```

#### 4.5 进程卡住了，在等什么

```
$ sudo strace -p 54
strace: Process 54 attached
restart_syscall(<... resuming interrupted clock_nanosleep ...>
```

这个 sleep 进程停在 `clock_nanosleep` 上（在睡眠）。卡在 `read`、`recvfrom` 通常是在等网络或管道的数据，卡在 `futex` 是在等锁。按 `Ctrl+C` 结束跟踪，被跟踪的进程不受影响。

### 5. ⚠️ 踩坑警告

| 现象 | 原因 | 怎么改 |
|---|---|---|
| `strace -p` 报 `Operation not permitted` | 跟踪其他用户的进程需要 root，Ubuntu 还默认限制了同一用户之间的跟踪（`kernel.yama.ptrace_scope = 1`） | 加 sudo |
| 在生产环境跟踪高负载进程，服务明显变慢 | strace 会让每个系统调用都暂停一下 | 尽量加 `-e` 过滤，跟踪时间尽量短 |

> ⚠️ 第一条未实机验证（测试环境以 root 执行）。

### 6. 一句话总结

报错含糊就 `strace -f -e trace=openat,connect 命令`，找 ENOENT 和失败的连接。

## 205 ★&nbsp;&nbsp;ltrace：跟踪库函数调用

> 级别：★ 高级 · 软件包：`ltrace`（0.7.91）

### 1. 作用

`ltrace` 和 strace 类似，但跟踪的是程序调用的**动态库函数**（如 C 库的 `strlen`、`malloc`、`getenv`），而不是系统调用。能看到程序读了哪些环境变量、比较了哪些字符串，对分析没有源码的 C/C++ 程序有用。

### 2. 基本格式

```bash
ltrace [参数] 命令
ltrace -p PID
```

| 参数 | 作用 |
|---|---|
| `-e 函数名` | 只跟踪指定的函数，如 `-e getenv` |
| `-c` | 统计调用次数和耗时 |
| `-f` | 跟踪子进程 |
| `-S` | 同时显示系统调用 |

### 3. 常用示例

```
$ ltrace python3 -c "pass" | head -3
syscall(318, 0x7fff10bdf900, 32, 1)              = 32
__cxa_atexit(0x6794a0, 0, 0, 0xfa95b943)         = 0
pthread_key_create(0, 0x4ee2ab)                  = 0
```

每行是一次库函数调用，等号后面是返回值。

```bash
ltrace -e getenv ./app      # 程序读取了哪些环境变量
```

### 4. ⚠️ 踩坑警告

| 现象 | 原因 | 怎么改 |
|---|---|---|
| 对很多现代程序运行 ltrace，什么都看不到 | 程序是静态链接的，或者用了“立即绑定”编译选项 | 改用 strace，或用 gdb 设断点 |

> ⚠️ 第一条未实机验证。

### 5. 一句话总结

想看程序调用了哪些库函数、读了哪些环境变量，用 `ltrace -e 函数 命令`。

## 206 ★&nbsp;&nbsp;gdb：调试器

> 级别：★ 高级 · 软件包：`gdb`（17.1）

### 1. 作用

`gdb` 是 GNU 调试器，可以让程序停在指定的位置（断点）、一行一行执行、查看变量和调用栈，也能附加到一个正在运行的进程上，或者分析程序崩溃留下的 core 文件。运维场景里最常用的是两件事：进程卡死时看它卡在哪；程序崩溃后看崩在哪。

### 2. 基本格式

```bash
gdb 程序                          # 启动调试
sudo gdb -p PID                    # 附加到运行中的进程
gdb 程序 core文件                  # 分析崩溃转储
gdb -batch -ex "命令" ...          # 不进入交互界面，执行命令后退出
```

### 3. 常用命令（在 gdb 里输入）

| 命令 | 作用 |
|---|---|
| `bt` | 调用栈（backtrace），崩溃或卡死时最先看 |
| `info threads` | 所有线程 |
| `thread apply all bt` | 所有线程的调用栈 |
| `break 函数或文件:行` | 设断点 |
| `run` / `continue` | 运行 / 继续 |
| `next` / `step` | 下一行 / 进入函数 |
| `print 变量` | 查看变量 |
| `detach` / `quit` | 脱离进程 / 退出 |

### 4. 常用示例

附加到一个运行中的 python 进程，看它的线程：

```
$ sudo gdb -p 86 -batch -ex "info threads"
...
[Thread debugging using libthread_db enabled]
* 1    Thread 0x7f7a5d93e1c0 (LWP 86) "python3" 0x00007f7a5d6a05ae in ?? () from /usr/lib/x86_64-linux-gnu/libc.so.6
[Inferior 1 (process 86) detached]
```

`-batch` 执行完就自动脱离，进程继续运行。

进程卡死，一次性导出所有线程的调用栈发给开发：

```bash
sudo gdb -p PID -batch -ex "thread apply all bt" > stack.txt
```

分析崩溃：

```bash
coredumpctl debug myapp        # 直接用 gdb 打开最近一次崩溃，然后输入 bt
```

### 5. ⚠️ 踩坑警告

| 现象 | 原因 | 怎么改 |
|---|---|---|
| 调用栈里全是 `??`，看不到函数名 | 程序没有调试符号 | 安装 `-dbgsym` 包；Ubuntu 的 gdb 会提示是否启用 debuginfod 自动下载符号 |
| 附加后忘了退出，服务一直不响应 | gdb 附加时进程是暂停的 | 及时 `detach`；或用 `-batch` |

### 6. 一句话总结

进程卡死用 `sudo gdb -p PID -batch -ex "thread apply all bt"` 导出调用栈。

## 223 ★&nbsp;&nbsp;kubectl：管理 Kubernetes 集群

> 级别：★ 高级 · 软件包：snap 版（`sudo snap install kubectl --classic`）或 MicroK8s 自带的 `microk8s kubectl`

### 1. 作用

Kubernetes（简称 K8s）是容器编排平台：把很多台机器组成一个集群，按声明的数量和配置自动运行、扩容、重启容器。`kubectl` 是它的命令行客户端，所有操作（部署应用、查看状态、看日志、进入容器）都通过它。

| 概念 | 含义 |
|---|---|
| Pod | 最小运行单位，一个或几个紧密相关的容器 |
| Deployment | 声明“这个应用要运行几个副本”，自动维持 |
| Service | 给一组 Pod 一个固定的访问地址 |
| Namespace | 把资源分组隔离，如 dev、prod |

### 2. 常用命令

| 命令 | 作用 |
|---|---|
| `kubectl get pods -A` | 所有命名空间的 Pod |
| `kubectl get deploy,svc -n 命名空间` | 部署和服务 |
| `kubectl describe pod 名称` | 详细信息和事件（排错最有用） |
| `kubectl logs -f 名称` | 日志 |
| `kubectl exec -it 名称 -- bash` | 进入容器 |
| `kubectl apply -f 文件.yaml` | 按配置文件创建或更新 |
| `kubectl scale deploy 名称 --replicas=3` | 调整副本数 |
| `kubectl rollout restart deploy 名称` | 滚动重启 |
| `kubectl delete -f 文件.yaml` | 删除 |

### 3. 常用示例

```bash
kubectl create deployment web --image=nginx:1.27 --replicas=2
kubectl expose deployment web --port=80 --type=NodePort
kubectl get pods -o wide
kubectl describe pod web-xxxxx
kubectl logs -f deploy/web
```

Pod 状态不是 Running 时，先 `describe` 看最下面的 Events：`ImagePullBackOff` 是镜像拉不下来，`CrashLoopBackOff` 是容器启动后反复崩溃（再看 logs），`Pending` 通常是资源不够或没有可用节点。

> ⚠️ 本页未实机验证：测试环境不能运行 Kubernetes 集群。命令为 kubectl 的标准用法。

### 4. 一句话总结

K8s 排错三步：`get pods` 看状态，`describe` 看事件，`logs` 看输出。

## 224 ★&nbsp;&nbsp;microk8s：单机即可运行的轻量 Kubernetes

> 级别：★ 高级 · 软件包：snap 版（`sudo snap install microk8s --classic`）

### 1. 作用

MicroK8s 是 Canonical 维护的轻量 Kubernetes 发行版，一条 snap 命令就能在一台 Ubuntu 上装好完整的 K8s，适合学习、开发测试、边缘设备，也可以多台组成集群。DNS、Ingress、存储、仪表盘等组件以“插件”形式按需启用。

### 2. 常用命令

| 命令 | 作用 |
|---|---|
| `microk8s status --wait-ready` | 等待就绪并显示已启用的插件 |
| `microk8s enable dns ingress hostpath-storage` | 启用插件 |
| `microk8s kubectl ...` | 自带的 kubectl |
| `microk8s add-node` | 生成让其他机器加入集群的命令 |
| `microk8s stop` / `start` | 停止 / 启动 |

### 3. 常用示例

```bash
sudo snap install microk8s --classic
sudo usermod -aG microk8s $USER     # 重新登录后不用 sudo
microk8s status --wait-ready
microk8s enable dns hostpath-storage
microk8s kubectl get nodes
alias kubectl='microk8s kubectl'
```

> ⚠️ 本页未实机验证：MicroK8s 需要 snapd 和 systemd，测试环境不具备。

### 4. 一句话总结

一台 Ubuntu 上体验 K8s：`sudo snap install microk8s --classic`，再 `enable dns`。

## 225 ★&nbsp;&nbsp;podman：不需要守护进程的容器工具

> 级别：★ 高级 · 软件包：`podman`（5.7.0）

### 1. 作用

`podman` 的命令和 [docker](#cmd-docker) 几乎完全一样（`podman run`、`podman ps`、`podman build`），区别是：

| | docker | podman |
|---|---|---|
| 后台服务 | 需要 dockerd 一直运行，并以 root 身份运行 | 不需要，每个容器是普通进程 |
| 普通用户运行容器 | 加入 docker 组（等同于获得 root 权限） | 原生支持 rootless，更安全 |
| 开机自启 | `--restart` | 生成 systemd 单元，或用 Quadlet 配置文件 |
| Pod | 无 | 支持把多个容器组成一个 Pod，和 K8s 的概念一致 |

很多人直接 `alias docker=podman` 使用。

### 2. 常用命令

和 docker 相同：`run`、`ps`、`images`、`pull`、`logs`、`exec`、`stop`、`rm`、`build`。另外：

| 命令 | 作用 |
|---|---|
| `podman info` | 运行环境信息（是否 rootless、存储驱动） |
| `podman pod create --name 名称` | 创建 Pod |
| `podman generate kube 容器` | 把容器导出成 Kubernetes 的 YAML |

### 3. 常用示例

```
$ podman --version
podman version 5.7.0
```

```bash
podman run -d --name web -p 8080:80 docker.io/library/nginx:1.27
podman ps
podman logs web
```

镜像名建议写全（`docker.io/library/nginx`），否则 podman 会让你在几个镜像仓库之间选择。

开机自启推荐用 Quadlet：在 `~/.config/containers/systemd/web.container`（rootless）或 `/etc/containers/systemd/` 下写一个配置文件，systemd 会自动生成服务。

> ⚠️ 运行容器的部分未实机验证：测试环境的容器里无法再运行容器。

### 4. 一句话总结

想用 docker 的命令又不想要 root 守护进程，就用 `podman`。

## 226 ★&nbsp;&nbsp;docker compose：用一个文件编排多个容器

> 级别：★ 高级 · 软件包：`docker-compose-v2`（Docker Compose 2.40）

### 1. 作用

一个应用通常需要好几个容器：Web、数据库、缓存。逐个 `docker run` 要写很长的参数，还要记住启动顺序。`docker compose` 把这些写进一个 `compose.yaml` 文件，一条命令启动、停止、升级整套服务。

注意新写法是 `docker compose`（空格，Docker 的子命令），旧版本的独立程序 `docker-compose`（连字符）已经停止维护。

### 2. 常用命令

在 compose.yaml 所在的目录执行：

| 命令 | 作用 |
|---|---|
| `docker compose up -d` | 后台启动全部服务（不存在则创建，配置变了则重建） |
| `docker compose ps` | 服务状态 |
| `docker compose logs -f [服务]` | 日志 |
| `docker compose exec 服务 bash` | 进入某个服务的容器 |
| `docker compose pull && docker compose up -d` | 拉取新镜像并升级 |
| `docker compose down` | 停止并删除容器（数据卷保留） |
| `docker compose config` | 检查并显示合并、替换变量后的最终配置 |

### 3. 常用示例

`compose.yaml`：

```yaml
services:
  web:
    image: nginx:1.27
    ports:
      - "8080:80"
    volumes:
      - ./html:/usr/share/nginx/html:ro
    restart: unless-stopped
  db:
    image: mysql:8.4
    environment:
      MYSQL_ROOT_PASSWORD: ${DB_PASS}
    volumes:
      - dbdata:/var/lib/mysql
volumes:
  dbdata:
```

同一目录下的 `.env` 文件：

```
DB_PASS=Db@2026
```

`${DB_PASS}` 会被替换成 .env 里的值，密码就不用写在 compose.yaml 里。

启动前先检查配置：

```
$ docker compose config
name: app
services:
  db:
    environment:
      MYSQL_ROOT_PASSWORD: Db@2026
    image: mysql:8.4
...
  web:
    image: nginx:1.27
...
    ports:
      - mode: ingress
        target: 80
        published: "8080"
        protocol: tcp
    restart: unless-stopped
...

$ docker compose config --services
db
web
```

缩进写错时：

```
$ docker compose -f bad.yaml config
yaml: line 1: did not find expected key
```

然后：

```bash
docker compose up -d
docker compose ps
```

> ⚠️ `up`、`ps` 等需要 Docker 守护进程的命令未实机验证（测试环境报 `Cannot connect to the Docker daemon`）；`config` 为实测。

### 4. ⚠️ 踩坑警告

| 现象 | 原因 | 怎么改 |
|---|---|---|
| `docker compose down -v` 后数据库数据没了 | `-v` 会连数据卷一起删除 | 平时只用 `down` |
| `.env` 里的密码被提交进了 git | .env 和 compose.yaml 放在一起 | 把 .env 写进 .gitignore |
| 改了 compose.yaml，执行 `restart` 没生效 | restart 只重启容器，不读取新配置 | 用 `up -d` |

### 5. 一句话总结

多容器写进 compose.yaml，`config` 检查、`up -d` 启动、`down` 停止。

## 295 ★&nbsp;&nbsp;ansible：批量自动化运维

> 级别：★ 高级 · 软件包：`ansible-core`（2.20）或 `ansible`

### 1. 作用

管理 3 台服务器可以逐台 ssh；管理 30 台、300 台就需要自动化。`ansible` 通过 ssh 连接到一批服务器，按你写的“剧本”（playbook）执行：装软件、改配置、建用户、重启服务。被管理的机器上**不需要装任何客户端**，只要能 ssh 登录、有 Python。

剧本是声明式的：写的是“目标状态”（这个目录应该存在，这个文件应该是这个内容），而不是“执行步骤”。已经符合的不会重复执行，所以同一个剧本可以放心地反复运行。

### 2. 基本组成

| 部分 | 作用 |
|---|---|
| 清单（inventory） | 有哪些服务器，怎么分组，通常写在 `hosts.ini` |
| 模块（module） | 具体做一件事，如 `apt`、`copy`、`file`、`service`、`user` |
| 剧本（playbook） | 一组任务，写在 YAML 文件里 |

清单示例 `hosts.ini`：

```ini
[web]
192.168.1.21
192.168.1.22

[db]
192.168.1.30 ansible_user=ops
```

### 3. 常用命令

| 命令 | 作用 |
|---|---|
| `ansible 组 -i hosts.ini -m ping` | 测试能否连接 |
| `ansible 组 -i hosts.ini -m command -a "命令"` | 在一批机器上执行命令 |
| `ansible-playbook -i hosts.ini 剧本.yml` | 执行剧本 |
| `ansible-playbook ... --check --diff` | 模拟执行，显示会改什么 |
| `ansible-playbook ... --limit 主机` | 只对某台机器执行 |

### 4. 常用示例

对本机演示：

```
$ ansible localhost -m ping
[WARNING]: No inventory was parsed, only implicit localhost is available
localhost | SUCCESS => {
    "changed": false,
    "ping": "pong"
}

$ ansible localhost -m command -a "uptime -p"
[WARNING]: No inventory was parsed, only implicit localhost is available
localhost | CHANGED | rc=0 >>
up 4 hours, 34 minutes
```

剧本 `site.yml`：

```yaml
- hosts: localhost
  gather_facts: false
  tasks:
    - name: 建目录
      ansible.builtin.file:
        path: /tmp/ansible-demo
        state: directory
        mode: "0755"
    - name: 写配置
      ansible.builtin.copy:
        dest: /tmp/ansible-demo/app.conf
        content: "port=8080\n"
```

第一次执行：

```
$ ansible-playbook site.yml
...
TASK [写配置] ******************************************************************
changed: [localhost]

PLAY RECAP *********************************************************************
localhost                  : ok=2    changed=2    unreachable=0    failed=0    skipped=0    rescued=0    ignored=0
```

马上再执行一次：

```
$ ansible-playbook site.yml
...
PLAY RECAP *********************************************************************
localhost                  : ok=2    changed=0    unreachable=0    failed=0    skipped=0    rescued=0    ignored=0
```

第二次 `changed=0`：目录和文件已经是目标状态，ansible 什么也没改。

### 5. ⚠️ 踩坑警告

| 现象 | 原因 | 怎么改 |
|---|---|---|
| 大量使用 `command`、`shell` 模块，每次执行都显示 changed | 这两个模块不知道命令有没有真的改动系统 | 优先用专门的模块（apt、copy、service），它们会先检查当前状态 |
| 一个剧本推到所有服务器后才发现写错了 | 没有先在少量机器上验证 | 先 `--check --diff`，再 `--limit` 一台试，最后全量 |
| 需要 sudo 的任务失败 | 没有提权 | 在 play 里加 `become: true` |

### 6. 一句话总结

批量管理服务器用 ansible：写剧本，先 `--check`，再 `--limit` 一台，最后全量。
