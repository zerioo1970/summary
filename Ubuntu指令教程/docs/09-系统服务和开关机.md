## 038 ★★★&nbsp;&nbsp;reboot：重启系统

> 级别：★★★ 初级 · 软件包：`systemd`（`reboot` 是指向 `systemctl` 的链接）

### 1. 作用

`reboot` 立即重启计算机。升级内核、改了某些系统配置之后需要重启才能生效。

重启会中断所有正在运行的程序和所有人的连接。在服务器上执行前，确认没有人正在使用，重要服务已经安排好。

### 2. 基本格式

```bash
sudo reboot
```

### 3. 常用参数

| 写法 | 作用 |
|---|---|
| `sudo reboot` | 立即重启 |
| `sudo systemctl reboot` | 效果相同，是 reboot 实际调用的命令 |
| `sudo shutdown -r +10` | 10 分钟后重启，并通知已登录的用户（见 [shutdown](#cmd-shutdown)） |

### 4. 常用示例

#### 4.1 判断是否需要重启

```bash
cat /var/run/reboot-required
```

`apt upgrade` 升级了内核或核心库之后，Ubuntu 会创建这个文件，内容是 `*** System restart required ***`。文件不存在就说明暂时不需要重启。需要重启的软件包列在 `/var/run/reboot-required.pkgs` 里。

#### 4.2 远程服务器重启后重新连接

```bash
sudo reboot
# ssh 连接会断开，等 1–2 分钟后重新 ssh 登录
uptime        # 确认刚刚重启过：up 后面的时间只有几分钟
```

> ⚠️ 本页未实机验证：测试环境不是完整的系统（没有 systemd），无法执行重启。命令写法为 Ubuntu 长期稳定的用法。

### 5. ⚠️ 踩坑警告

| 现象 | 原因 | 怎么改 |
|---|---|---|
| 在一台 ssh 窗口里执行了 reboot，重启的却是生产服务器 | 开了多个 ssh 窗口，搞混了 | 执行前看一眼提示符里的主机名，或先执行 `hostname` |
| 重启后服务没有自动起来 | 服务没有设为开机自启 | `sudo systemctl enable 服务名` |
| 重启后连不上服务器 | 网络配置（netplan）或防火墙改错了，重启后才生效 | 改网络配置前确认有控制台（云服务器的 VNC 控制台、机房 KVM）可以兜底 |

### 6. 一句话总结

`sudo reboot` 立即重启；先确认主机名，有 `/var/run/reboot-required` 才需要重启。

## 039 ★★★&nbsp;&nbsp;shutdown：关机或定时重启

> 级别：★★★ 初级 · 软件包：`systemd`（`shutdown` 是指向 `systemctl` 的链接）

### 1. 作用

`shutdown` 关闭或重启计算机，可以立即执行，也可以定时执行。定时执行时，会向所有已登录的用户发送通知，给他们时间保存工作。

### 2. 基本格式

```bash
sudo shutdown [参数] [时间] [通知内容]
```

| 时间写法 | 含义 |
|---|---|
| `now` | 立即 |
| `+10` | 10 分钟后 |
| `23:30` | 今天 23:30（24 小时制） |

不写时间时，默认是 1 分钟后。

### 3. 常用参数

| 参数 | 作用 |
|---|---|
| `-h` | 关机（默认行为） |
| `-r` | 重启 |
| `-c` | 取消已经安排的关机/重启 |

### 4. 常用示例

```bash
sudo shutdown -h now                              # 立即关机
sudo shutdown -r +10 "10 分钟后重启，请保存工作"  # 10 分钟后重启，并通知所有人
sudo shutdown -r 23:30                            # 今晚 23:30 重启
sudo shutdown -c                                  # 取消
```

定时之后，到点前 5 分钟系统会禁止新用户登录。

另外两个常用的关机写法：

| 命令 | 效果 |
|---|---|
| `sudo poweroff` | 立即关机，等同 `shutdown -h now` |
| `sudo systemctl poweroff` | poweroff 实际调用的命令 |

> ⚠️ 本页未实机验证：测试环境不是完整的系统（没有 systemd），无法执行关机。命令写法为 Ubuntu 长期稳定的用法。

### 5. ⚠️ 踩坑警告

| 现象 | 原因 | 怎么改 |
|---|---|---|
| 想重启，结果把云服务器关机了，只能去控制台开机 | 少写了 `-r` | 重启用 `sudo reboot` 或 `shutdown -r`，执行前再看一眼参数 |
| 远程服务器执行 `shutdown -h now` 后无法再连上 | 关机后需要有人按电源键或在控制台开机 | 远程维护只用重启，不用关机 |
| `shutdown -r 23:30` 之后又不想重启了 | 定时任务已经登记 | `sudo shutdown -c` |

### 6. 一句话总结

关机 `shutdown -h now`，定时重启 `shutdown -r +分钟`，反悔用 `-c`。

## 066 ★★★&nbsp;&nbsp;systemctl：管理系统服务

> 级别：★★★ 初级 · 软件包：`systemd`（Ubuntu 26.04 为 systemd 259）

### 1. 作用

`systemctl` 管理 systemd 下的服务（service，在后台长期运行的程序，比如 nginx、mysql、ssh）：启动、停止、重启、查看状态、设置开机自启。装好一个服务之后，几乎所有的日常操作都通过 systemctl 完成。

每个服务都对应一个**单元文件**（unit file），描述怎么启动它、失败了怎么办。系统自带的单元文件在 `/usr/lib/systemd/system/`，自己写的放 `/etc/systemd/system/`。

### 2. 基本格式

```bash
sudo systemctl 子命令 服务名
```

服务名后面的 `.service` 可以省略：`nginx` 等同 `nginx.service`。

### 3. 常用子命令

| 子命令 | 作用 |
|---|---|
| `status` | 查看状态和最近几行日志（不需要 sudo） |
| `start` / `stop` | 启动 / 停止 |
| `restart` | 重启 |
| `reload` | 重新加载配置，不中断服务（服务要支持才行） |
| `enable` / `disable` | 设置 / 取消开机自启 |
| `enable --now` | 设为开机自启并立即启动 |
| `is-active` / `is-enabled` | 只输出是否在运行 / 是否开机自启，适合脚本 |
| `list-units --type=service` | 列出正在运行的服务 |
| `list-unit-files` | 列出所有单元文件及其自启状态 |
| `cat 服务名` | 查看单元文件内容 |
| `daemon-reload` | 修改单元文件后，让 systemd 重新读取 |

### 4. 常用示例

> ⚠️ 本节中 start、stop、status 等需要 systemd 正在运行的命令未实机验证（测试环境没有以 systemd 启动）。`cat`、`list-unit-files`、`is-enabled` 已在 Ubuntu 26.04 实测。

#### 4.1 日常操作

```bash
systemctl status nginx            # 看状态
sudo systemctl restart nginx      # 改了配置后重启
sudo systemctl reload nginx       # 或者只重新加载配置
sudo systemctl enable --now nginx # 开机自启并立即启动
```

`status` 的输出里，重点看这两行：

```
     Loaded: loaded (/usr/lib/systemd/system/nginx.service; enabled; preset: enabled)
     Active: active (running) since Thu 2026-10-29 08:00:00 UTC; 5min ago
```

`enabled` 表示开机自启；`active (running)` 表示正在运行。服务启动失败时，这里显示 `failed`，下面会跟着最近几行错误日志。

#### 4.2 `cat`：看服务是怎么启动的

```
$ systemctl cat ssh.service
# /usr/lib/systemd/system/ssh.service
[Unit]
Description=OpenBSD Secure Shell server
Documentation=man:sshd(8) man:sshd_config(5)
After=network.target nss-user-lookup.target auditd.service
ConditionPathExists=!/etc/ssh/sshd_not_to_be_run

[Service]
EnvironmentFile=-/etc/default/ssh
ExecStartPre=/usr/sbin/sshd -t
ExecStart=/usr/sbin/sshd -D $SSHD_OPTS
ExecReload=/usr/sbin/sshd -t
ExecReload=/bin/kill -HUP $MAINPID
KillMode=process
Restart=on-failure
...
```

`ExecStart` 是启动命令，`Restart=on-failure` 表示进程异常退出时自动拉起。

#### 4.3 查看开机自启的单元

```
$ systemctl list-unit-files --state=enabled
UNIT FILE                       STATE   PRESET
cron.service                    enabled enabled
e2scrub_reap.service            enabled enabled
getty@.service                  enabled enabled
sshd-keygen.service             enabled enabled
systemd-pstore.service          enabled enabled
systemd-resolved.service        enabled enabled
systemd-timesyncd.service       enabled enabled
wtmpdb-update-boot.service      enabled enabled
ssh.socket                      enabled enabled
...
```

#### 4.4 Ubuntu 26.04 的 ssh 是按需启动的

```
$ systemctl list-unit-files "ssh*"
UNIT FILE           STATE    PRESET
ssh.service         disabled enabled
sshd-keygen.service enabled  enabled
sshd.service        alias    -
sshd@.service       static   -
ssh.socket          enabled  enabled
ssh-access.target   static   -

6 unit files listed.
```

`ssh.service` 是 disabled，开机自启的是 `ssh.socket`：systemd 先替 ssh 监听 22 端口，有人连接时才启动 sshd。所以改 ssh 端口时，只改 `/etc/ssh/sshd_config` 后重启 ssh.service 不一定生效，还需要 `sudo systemctl daemon-reload` 并重启 `ssh.socket`。

#### 4.5 脚本里判断服务是否在运行

```bash
if systemctl is-active --quiet nginx; then
    echo "nginx 正在运行"
fi
```

### 5. ⚠️ 踩坑警告

| 现象 | 原因 | 怎么改 |
|---|---|---|
| 改了单元文件，重启服务后没有变化，还提示 `Run 'systemctl daemon-reload' to reload units` | systemd 缓存了旧的单元文件 | `sudo systemctl daemon-reload` 后再重启 |
| `start` 了服务，重启服务器后它没起来 | start 只管这一次，不设开机自启 | `sudo systemctl enable 服务名` |
| 服务启动失败，status 里只看到几行日志 | status 只显示最近 10 行 | 用 `journalctl -u 服务名 -e` 看完整日志 |
| 在容器里报 `System has not been booted with systemd as init system (PID 1). Can't operate.` | 容器里通常没有运行 systemd | 在容器里直接运行程序，不用 systemctl |
| 直接修改 `/usr/lib/systemd/system/` 下的文件，升级软件后改动消失 | 那是软件包管理的文件，会被覆盖 | 用 `sudo systemctl edit 服务名` 写覆盖配置，保存在 `/etc/systemd/system/` |

第四条的实测：

```
$ systemctl status ssh
System has not been booted with systemd as init system (PID 1). Can't operate.
Failed to connect to system scope bus via local transport: Host is down
```

### 6. 一句话总结

`status` 看状态，`restart` 重启，`enable --now` 开机自启；改单元文件后先 `daemon-reload`。

## 101 ★★&nbsp;&nbsp;journalctl：查看 systemd 日志

> 级别：★★ 中级 · 软件包：`systemd`（systemd 259）

### 1. 作用

Ubuntu 上，systemd 管理的服务（nginx、ssh、cron，以及你自己写的服务）的输出、内核消息、登录记录，都由 journald 统一收集。`journalctl` 用来查询这些日志，可以按服务、按时间、按级别筛选，还能像 `tail -f` 一样实时跟踪。

服务启动失败时，`systemctl status` 只显示最后几行；完整的错误原因要用 journalctl 看。

### 2. 基本格式

```bash
journalctl [参数]
```

查看系统服务的日志需要 sudo，或者把用户加入 `adm` 组或 `systemd-journal` 组。

### 3. 常用参数

| 参数 | 作用 |
|---|---|
| `-u 服务` | 只看某个服务的日志，如 `-u nginx` |
| `-f` | 实时跟踪新日志 |
| `-e` | 打开后直接跳到末尾 |
| `-n 行数` | 只看最后 N 行 |
| `--since` / `--until` | 时间范围，如 `--since "2026-10-29 09:00"`、`--since today`、`--since "1 hour ago"` |
| `-p 级别` | 按级别过滤，如 `-p err`（错误及以上） |
| `-b` | 本次开机以来的日志；`-b -1` 是上一次开机 |
| `-k` | 只看内核消息（等同 dmesg） |
| `--no-pager` | 不分页，直接输出（脚本里用） |
| `-o 格式` | 输出格式，`short-iso` 带完整日期，`json` 方便程序处理 |
| `--disk-usage` | 日志占了多少磁盘空间 |
| `--vacuum-size=大小` | 删除旧日志，直到总大小不超过指定值 |

日志级别从高到低：`emerg` `alert` `crit` `err` `warning` `notice` `info` `debug`。

### 4. 常用示例

> ⚠️ 本节未实机验证：测试环境没有运行 journald，`journalctl` 输出 `No journal files were found.`。参数已对照 systemd 259 的手册核实。

#### 4.1 服务启动失败，看完整原因

```bash
sudo systemctl start myapp       # 失败
sudo journalctl -u myapp -e      # 跳到末尾看最新的错误
```

#### 4.2 实时跟踪

```bash
sudo journalctl -u nginx -f
```

效果和 `tail -f` 相同，按 `Ctrl+C` 退出。

#### 4.3 按时间和级别查

```bash
sudo journalctl --since "2026-10-29 09:00" --until "2026-10-29 10:00"
sudo journalctl -p err --since today
sudo journalctl -u ssh --since "1 hour ago" | grep "Failed password"
```

#### 4.4 服务器意外重启，看重启前发生了什么

```bash
journalctl --list-boots          # 列出历次开机
sudo journalctl -b -1 -e         # 上一次开机的日志，跳到末尾
```

#### 4.5 日志占满了磁盘

```bash
journalctl --disk-usage
sudo journalctl --vacuum-size=500M
```

要永久限制大小，在 `/etc/systemd/journald.conf` 里设置 `SystemMaxUse=500M`，然后 `sudo systemctl restart systemd-journald`。

### 5. ⚠️ 踩坑警告

| 现象 | 原因 | 怎么改 |
|---|---|---|
| 不加 sudo 只能看到很少的日志 | 普通用户只能看自己的日志 | 加 sudo，或 `sudo usermod -aG adm 用户` |
| 重启后 `-b -1` 报 `Specifying boot ID or boot offset has no effect, no persistent journal was found` | 日志只保存在内存里，没有持久化 | 确认 `/var/log/journal/` 目录存在；Ubuntu 默认是持久化的 |
| 在容器里报 `No journal files were found.` | 容器里没有运行 journald | 用 `docker logs` 等容器自己的日志命令 |

> ⚠️ 第二条的提示文字未实机验证。

### 6. 一句话总结

服务出错用 `sudo journalctl -u 服务 -e`，实时看加 `-f`，按时间用 `--since`。

## 190 ★★&nbsp;&nbsp;systemd-analyze：分析开机耗时和时间表达式

> 级别：★★ 中级 · 软件包：`systemd`

### 1. 作用

`systemd-analyze` 有两类常用功能：

- **开机分析**：开机一共花了多久，哪个服务拖慢了开机。
- **工具功能**：检查 systemd 定时器的时间表达式是否写对、单元文件是否有错。这些不需要系统正在运行 systemd，在哪里都能用。

### 2. 基本格式

```bash
systemd-analyze [子命令] [参数]
```

### 3. 常用子命令

| 子命令 | 作用 |
|---|---|
| （不写） | 开机总耗时，分内核、initrd、用户空间三段 |
| `blame` | 按耗时列出每个服务的启动时间 |
| `critical-chain` | 开机过程中最慢的那条依赖链 |
| `calendar "表达式"` | 解析定时器的时间表达式，显示下次触发的时间 |
| `timespan "时长"` | 解析时间长度的写法 |
| `verify 单元文件` | 检查单元文件有没有错误 |

### 4. 常用示例

#### 4.1 开机为什么慢

```bash
systemd-analyze
systemd-analyze blame | head
systemd-analyze critical-chain
```

最常见的“慢”是 `systemd-networkd-wait-online.service`：开机时等待网络就绪，网卡配置有问题时会一直等到超时（通常两分钟）。

> ⚠️ 4.1 未实机验证（测试环境没有以 systemd 启动）。

#### 4.2 检查定时器的时间写法

systemd 定时器用 `OnCalendar=` 写执行时间，格式和 crontab 不同，写之前用 calendar 验证：

```
$ systemd-analyze calendar daily
  Original form: daily
Normalized form: *-*-* 00:00:00
    Next elapse: Fri 2026-10-30 00:00:00 UTC
       From now: 15h left

$ systemd-analyze calendar "Mon..Fri 09:00"
  Original form: Mon..Fri 09:00
Normalized form: Mon..Fri *-*-* 09:00:00
    Next elapse: Thu 2026-10-29 09:00:00 UTC
       From now: 18min left
```

看接下来的几次触发时间：

```
$ systemd-analyze calendar "*-*-* 02:30:00" --iterations=3
Normalized form: *-*-* 02:30:00
    Next elapse: Fri 2026-10-30 02:30:00 UTC
       From now: 17h left
   Iteration #2: Sat 2026-10-31 02:30:00 UTC
       From now: 1 day 17h left
   Iteration #3: Sun 2026-11-01 02:30:00 UTC
       From now: 2 days left
```

#### 4.3 时间长度的写法

```
$ systemd-analyze timespan "1h 30min"
Original: 1h 30min
      μs: 5400000000
   Human: 1h 30min
```

单元文件里 `TimeoutStartSec=`、`RestartSec=` 这类设置用的就是这种写法。

#### 4.4 检查自己写的单元文件

```bash
systemd-analyze verify /etc/systemd/system/myapp.service
```

没有输出表示没发现问题；有错误时会指出哪一行、哪个配置项。

### 5. 一句话总结

开机慢用 `systemd-analyze blame`，写定时器前用 `systemd-analyze calendar` 验证。

## 242 ★&nbsp;&nbsp;systemd-cgls：查看 cgroup 树

> 级别：★ 高级 · 软件包：`systemd`

### 1. 作用

systemd 用 cgroup（control group，控制组）把进程分组：每个服务一个组，每个用户会话一个组，然后按组限制 CPU、内存、IO。`systemd-cgls` 以树形列出这些分组以及每组里有哪些进程，能直观看出“这个进程属于哪个服务”。

### 2. 基本格式

```bash
systemd-cgls [cgroup路径]
systemd-cgls -u 服务名      # 只看某个服务
```

### 3. 常用示例

```bash
systemd-cgls
systemd-cgls -u nginx.service
```

在普通 Ubuntu 上，输出的第一层是 `user.slice`（用户会话）、`system.slice`（系统服务）和 `init.scope`（1 号进程），`system.slice` 下每个服务一个分支，列出它的主进程和子进程。

> ⚠️ 本页未实机验证：测试环境没有以 systemd 启动，只输出了 `CGroup /:` 和 `-.slice` 两行。

### 4. 一句话总结

不知道某个进程是哪个服务拉起来的，用 `systemd-cgls` 看树。

<a id="cmd-systemd-run"></a>

## 243 ★&nbsp;&nbsp;systemd-run：在临时单元里运行命令

> 级别：★ 高级 · 软件包：`systemd`

### 1. 作用

`systemd-run` 把一条命令放进一个临时的 systemd 单元里运行。好处是可以直接给它加上资源限制（最多用多少内存、多少 CPU），日志也会进入 journal，还能用 systemctl 管理。不用写单元文件就能做到“限制内存跑一个脚本”“30 分钟后执行一次”。

### 2. 基本格式

```bash
sudo systemd-run [参数] 命令
```

### 3. 常用参数

| 参数 | 作用 |
|---|---|
| `--scope` | 在前台运行，输出直接显示在终端 |
| `-p 属性=值` | 资源限制，如 `-p MemoryMax=500M`、`-p CPUQuota=50%` |
| `--unit=名称` | 给临时单元起名，之后可以 `systemctl status 名称` |
| `--on-calendar=时间` | 定时执行（会同时创建一个临时定时器） |
| `--on-active=时长` | 多久之后执行一次，如 `--on-active=30m` |
| `--user` | 以当前用户身份运行在用户管理器中 |

### 4. 常用示例

```bash
sudo systemd-run --scope -p MemoryMax=500M -p CPUQuota=50% python3 import_data.py
sudo systemd-run --unit=export-job --on-active=30m /opt/scripts/export.sh
systemctl status export-job.timer
journalctl -u export-job
```

第一条：导入脚本最多用 500 MB 内存、半个 CPU 核，超过内存限制会被系统结束，不会拖垮整台机器。

> ⚠️ 本页未实机验证：测试环境没有以 systemd 启动，systemd-run 报 `System has not been booted with systemd as init system (PID 1). Can't operate.`

### 5. 一句话总结

临时限制资源跑一个任务：`sudo systemd-run --scope -p MemoryMax=500M 命令`。

<a id="cmd-systemd-cgtop"></a>

## 244 ★&nbsp;&nbsp;systemd-cgtop：按 cgroup 查看资源占用

> 级别：★ 高级 · 软件包：`systemd`

### 1. 作用

`systemd-cgtop` 和 top 类似，但统计的单位是 cgroup（服务、用户会话），而不是单个进程。一个服务有几十个子进程时（如 php-fpm、Apache、Java 应用），top 里看到的是分散的一堆进程，cgtop 能直接告诉你“这个服务一共占了多少 CPU 和内存”。

### 2. 基本格式

```bash
systemd-cgtop [参数]
```

| 参数 | 作用 |
|---|---|
| `-m` / `-c` | 按内存 / CPU 排序 |
| `-d 秒` | 刷新间隔 |
| `-b -n 次数` | 批处理模式，输出几次就退出 |

### 3. 常用示例

```bash
sudo systemd-cgtop -m
```

输出的列依次是：控制组路径、任务数（Tasks）、%CPU、内存（Memory）、读写速度（Input/s、Output/s）。

> ⚠️ 本页未实机验证：测试环境只有一个根 cgroup，批处理模式只输出了一行 `/     14078      -        -        -        -`。

### 4. 一句话总结

想知道每个服务总共占了多少资源，用 `sudo systemd-cgtop`。

<a id="cmd-logrotate"></a>

## 279 ★&nbsp;&nbsp;logrotate：日志轮转

> 级别：★ 高级 · 软件包：`logrotate`（3.22）

### 1. 作用

程序的日志会一直变大，最终写满磁盘。`logrotate` 定期“轮转”日志：把当前的 app.log 改名为 app.log.1、压缩旧的、删除太旧的，再让程序写一个新的 app.log。Ubuntu 每天通过定时任务自动运行它，系统日志、apt、nginx 等软件都已经配好了。自己写的程序，只需要在 `/etc/logrotate.d/` 下加一个配置文件。

### 2. 配置文件

| 位置 | 作用 |
|---|---|
| `/etc/logrotate.conf` | 全局默认值 |
| `/etc/logrotate.d/` | 每个软件一个文件 |

```
$ cat /etc/logrotate.d/apt
/var/log/apt/term.log {
  rotate 12
  monthly
  compress
  missingok
  notifempty
}
...
```

### 3. 常用配置项

| 配置项 | 含义 |
|---|---|
| `daily` / `weekly` / `monthly` | 多久轮转一次 |
| `rotate 14` | 保留 14 份旧日志，更早的删除 |
| `compress` | 旧日志用 gzip 压缩 |
| `delaycompress` | 最近一份旧日志（.1）暂不压缩，下一次再压缩 |
| `missingok` | 日志文件不存在也不报错 |
| `notifempty` | 日志是空的就不轮转 |
| `size 100M` | 超过这个大小才轮转 |
| `copytruncate` | 复制一份再清空原文件，程序不需要重新打开文件 |
| `create 640 用户 组` | 轮转后新建日志文件，并设定权限 |
| `postrotate ... endscript` | 轮转后执行的命令，如通知程序重新打开日志 |

### 4. 常用示例

给自己的程序配置轮转，`/etc/logrotate.d/priceapp`：

```
/var/log/priceapp/*.log {
    daily
    rotate 14
    compress
    delaycompress
    missingok
    notifempty
    copytruncate
}
```

先用 `-d` 检查（只打印要做什么，不真的执行）：

```
$ sudo logrotate -d /etc/logrotate.d/priceapp
warning: logrotate in debug mode does nothing except printing debug messages!  Consider using verbose mode (-v) instead if this is not what you want.

reading config file /etc/logrotate.d/priceapp
...
rotating pattern: /var/log/priceapp/*.log after 1 days empty log files are not rotated, (14 rotations), old logs are removed
considering log /var/log/priceapp/app.log
...
```

`-f` 强制立即轮转一次，验证效果：

```
$ sudo logrotate -f /etc/logrotate.d/priceapp; ls -l /var/log/priceapp/
total 4
-rw-r--r-- 1 root root  0 Oct 29 10:08 app.log
-rw-r--r-- 1 root root 21 Oct 29 10:08 app.log.1
```

原来的内容到了 app.log.1，app.log 被清空。因为有 `delaycompress`，app.log.1 暂时没有压缩。马上再执行一次 `-f`，文件没有变化，因为 app.log 是空的，`notifempty` 让它跳过了。

### 5. ⚠️ 踩坑警告

| 现象 | 原因 | 怎么改 |
|---|---|---|
| 轮转后，程序还在往 app.log.1 里写，新的 app.log 一直是空的 | 程序一直开着原来那个文件，改名后它写的还是同一个文件 | 用 `copytruncate`；或在 `postrotate` 里让程序重新打开日志（如 `systemctl reload 服务`） |
| 用了 copytruncate，轮转那一瞬间丢了几行日志 | 复制和清空之间写入的内容会丢失 | 对日志完整性要求高时，改用 postrotate 通知程序的方式 |
| 自己写的配置没有生效 | 文件权限或语法有问题 | `sudo logrotate -d 配置文件` 检查 |

### 6. 一句话总结

自己程序的日志在 /etc/logrotate.d/ 加配置，`-d` 检查，`-f` 试一次。

## 280 ★&nbsp;&nbsp;logger：往系统日志里写一条记录

> 级别：★ 高级 · 软件包：`bsdutils`

### 1. 作用

`logger` 把一条消息写进系统日志（journal 和 syslog）。脚本里用它记录“备份开始”“备份失败”，这些记录会和系统的其他日志放在一起，可以用 journalctl 统一查询，也会被日志收集系统一起收走。

### 2. 基本格式

```bash
logger [参数] "消息"
```

| 参数 | 作用 |
|---|---|
| `-t 标签` | 标记是哪个程序写的，便于过滤 |
| `-p 设施.级别` | 优先级，如 `user.err`、`local0.info` |
| `-s` | 同时输出到屏幕（标准错误） |

### 3. 常用示例

```bash
logger -t backup "备份开始"
logger -t backup -p user.err "备份失败：磁盘已满"
journalctl -t backup --since today
```

在脚本里：

```bash
if ! tar -czf /backup/www.tar.gz /var/www; then
    logger -t backup -p user.err "网站备份失败"
    exit 1
fi
logger -t backup "网站备份完成"
```

> ⚠️ 查询部分未实机验证：测试环境没有运行日志服务，logger 执行成功（退出码 0）但消息没有地方接收。

### 4. 一句话总结

脚本里用 `logger -t 标签 "消息"` 写日志，`journalctl -t 标签` 查。

## 281 ★&nbsp;&nbsp;coredumpctl：查看程序崩溃的转储

> 级别：★ 高级 · 软件包：`systemd-coredump`

### 1. 作用

程序崩溃（段错误、异常退出）时，系统可以把它当时的内存状态保存成 core dump 文件，开发人员用调试器分析它就能找到崩溃在哪一行代码。安装了 systemd-coredump 后，这些转储由 systemd 统一收集，`coredumpctl` 用来列出、查看和导出。

### 2. 常用命令

| 命令 | 作用 |
|---|---|
| `coredumpctl list` | 列出所有崩溃记录：时间、PID、程序、信号 |
| `coredumpctl info PID或程序名` | 详细信息，包括崩溃时的调用栈 |
| `coredumpctl dump PID -o 文件` | 导出 core 文件，交给开发人员 |
| `coredumpctl debug PID` | 直接用 gdb 打开 |

### 3. 常用示例

```bash
coredumpctl list
coredumpctl info myapp
sudo coredumpctl dump 12345 -o myapp.core
```

core 文件保存在 `/var/lib/systemd/coredump/`，默认会自动清理旧的。

> ⚠️ 本页未实机验证：测试环境没有 journald，`coredumpctl list` 输出 `No journal files were found.` 和 `No coredumps found.`。

### 4. 一句话总结

程序崩溃后 `coredumpctl list` 找记录，`info` 看调用栈，`dump` 导出给开发。

<a id="cmd-busctl"></a>

## 282 ★&nbsp;&nbsp;busctl：查看和调用 D-Bus

> 级别：★ 高级 · 软件包：`systemd`

### 1. 作用

D-Bus 是 Linux 上程序之间相互调用的消息总线。systemd、NetworkManager、桌面环境都通过它提供接口：hostnamectl、timedatectl 这些命令其实就是通过 D-Bus 调用 systemd 的服务。`busctl` 能列出总线上有哪些服务、查看它们提供的接口，并直接调用。主要用于排查和开发。

### 2. 常用命令

| 命令 | 作用 |
|---|---|
| `busctl list` | 列出总线上的所有服务 |
| `busctl tree 服务名` | 服务提供的对象树 |
| `busctl introspect 服务名 对象路径` | 对象的方法和属性 |
| `busctl get-property 服务 路径 接口 属性` | 读取一个属性 |
| `busctl monitor` | 实时查看总线上的消息 |

### 3. 常用示例

读取主机名（hostnamectl 背后做的就是这件事）：

```bash
busctl get-property org.freedesktop.hostname1 /org/freedesktop/hostname1 org.freedesktop.hostname1 Hostname
```

> ⚠️ 本页未实机验证：测试环境没有运行 D-Bus，busctl 报 `Failed to connect to system scope bus via local transport: No such file or directory`。

### 4. 一句话总结

`busctl list` 看有哪些 D-Bus 服务，排查 systemd 类命令的故障时用。
