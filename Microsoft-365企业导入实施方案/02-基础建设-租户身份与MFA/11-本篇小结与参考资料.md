## 本篇小结

第1篇做的是调查和决策，第2篇把决策变成了真实存在的企业云环境。本篇建立了三层基础：

**第一层：租户与管理边界（第1～2节）**

- 唯一的正式租户，且租户创建国家或地区、数据位置已核对留档——**这是不可回退的设置**。
- 管理账号与日常办公账号分离，全局管理员数量降到最低。
- 两个以上仅云紧急访问账号，使用初始域名、防钓鱼认证、排除阻断型策略，并按 90 天周期演练。
- 理解 Microsoft 的平台级强制 MFA 要求：管理门户、Azure CLI/PowerShell 等都已在要求范围内。

**第二层：域名与邮件信任（第3～4节）**

- 企业域名已验证，但**验证域名与切换 MX 是两件事**，切 MX 必须等邮箱全部创建后（第3篇）。
- 每个发信域只有一条 SPF 记录，涵盖全部合法来源，且未超过 10 次 DNS 查询。
- DKIM 的 CNAME 值来自门户或 `Get-DkimSigningConfig` 的实际输出，不能拼接。
- DMARC 从 `p=none` 起步，按 `quarantine → reject` 渐进，并有人真正在看 `rua` 报告。
- 理解**域对齐**：SPF 和 DKIM 都 pass，DMARC 仍可能 fail。

**第三层：身份与登录安全（第5～10节）**

- 命名规则先定、冲突先查，再批量创建账号与组。
- 混合身份先清理本地 AD、先小范围试点，属性在本地 AD 改而不是云端改。
- MFA 的主推方式是**防钓鱼**方式（passkey / Windows Hello / FIDO2 / 证书）。
- **2026-09-01 起 passkey 成为默认体验；2027-02-01 起 Microsoft 提供的短信与语音退役**，短信不能作为长期方案。
- 条件访问策略遵守“仅报告 → 小范围 → 分批 → 全量”，每次变更后用紧急账号验证。
- MFA 推广的成败取决于用户沟通、服务台准备和非人账号（打印机、业务系统）的改造。

### 本篇最重要的五条纪律

1. **租户地区选错不可回退**，创建前必须核对。
2. **先建邮箱，再切 MX**，顺序不能颠倒。
3. **任何阻断型策略都必须排除紧急访问账号**，且变更后立即用该账号登录验证。
4. **不要出现“关掉安全默认值但条件访问还没配好”的空档期**。
5. **短信验证不写入长期方案**，防钓鱼方式才是目标状态。

## 进入第3篇的条件

满足以下条件后，再进入第3篇（邮件：Exchange Online 配置与迁移）：

1. 租户唯一、地区与数据位置已核对，账单归属清楚。
2. 管理员体系可用，紧急访问账号演练通过并有告警。
3. 企业域名已验证；DNS 变更计划与回退方案已批准，但**MX 尚未切换**。
4. SPF 已规划、DKIM 已就绪、DMARC 处于可监控状态。
5. 用户账号与组已按命名规则创建，冲突检查通过。
6. 混合身份场景下，同步已稳定、错误已清零、回退方案已就绪。
7. MFA 已在管理员和至少一个部门范围内启用并验证。
8. 打印机、扫描仪、业务系统的发信改造方案已确定（可与第3篇并行实施）。

> **必做：** 第3篇会执行 MX 切换和邮件迁移，这是整个项目对业务影响最大的环节。上述条件如有未满足项，应先补齐或取得书面的风险接受，不要为了赶进度跳过。
