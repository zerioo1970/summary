## 本篇小结

第3篇是整个项目**对业务影响最大**的一篇。它分成两个明显不同的阶段：

**阶段一：把云端邮件系统建好（第 1～5 节）**

- 分清 Exchange Online（服务）与 Outlook（客户端）；分清用户邮箱、共享邮箱、资源邮箱。
- 共享邮箱有硬性规则：无许可上限 50 GB、扩到 100 GB 需 Plan 2、最多支持 25 名用户、**必须阻止其账号登录**。
- 把旧系统**每一个能收邮件的地址**都在云端建好，形成对照表——这是切 MX 的放行凭据。
- 邮件流规则先提示、后拦截；**外部自动转发默认阻止**；三个层面的转发都要查（邮箱级、收件箱规则、邮件流规则）。
- 邮件安全策略必须**在切 MX 之前**配好，优先使用预设安全策略；允许列表要有到期日期。
- BEC 无法仅靠技术拦住，必须配合**电话回拨 + 双人复核**的财务制度。
- 邮件追踪技能必须在切换前掌握，至少两名管理员各自演练过。

**阶段二：把历史邮件搬过来并切换（第 6～10 节）**

- 迁移方式由源系统能力、是否需要日历联系人、是否需要共存决定；**IMAP 通常迁不了日历和联系人**。
- 映射表要**双人核对**——迁错邮箱等于数据泄露事件。
- 有委派关系的用户**必须同批迁移**。
- 工期要用**试迁移实测速度**校准，并留 30%～50% 余量。
- 切换顺序不能变：停写 → 改 MX → 最后一次增量 → 完成批次 → 实测验证。
- 大邮箱、共享邮箱、委派用户、管理层**必须 100% 核对**，不能抽查。
- 切换后**连续至少 3 天**检查旧系统是否仍收到新邮件并补投。
- “邮箱迁完”不等于“可以拆旧系统”；下线需满足 D1～D12 全部条件。

### 本篇最重要的六条纪律

1. **先建齐所有收件对象，再切 MX。** 漏一个别名就是一条业务通道中断。
2. **共享邮箱必须阻止登录**，并逐个确认而非抽查。
3. **试迁移不通过，绝不进入批量迁移。**
4. **有委派关系的用户同批迁移。**
5. **切换前必须停写旧系统**，否则最后一次增量覆盖不全。
6. **回退门槛要高于普通变更** —— 邮件回退不干净，重点应放在“不需要回退”。

### 本篇涉及的三个关键时间线

| 事项 | 状态 | 对项目的影响 |
|---|---|---|
| **EWS 在 Exchange Online 的退役** | 自 **2026-10-01** 起开始阻止**非微软应用**的 EWS 请求；仅影响 Exchange Online，不影响 Exchange Server 与 Outlook、Teams 等微软产品 | **第三方迁移工具若仍依赖 EWS 可能停止工作**，选型前须取得厂商书面确认 |
| **Exchange Server 2016 / 2019 终止支持** | 已于 **2025-10-14** 结束；扩展安全更新程序将于 **2026 年 10 月**结束 | 混合迁移可行性、旧系统保留期与安全风险 |
| **旧版公共文件夹迁移限制** | 自 **2025-10-01** 起，Exchange Server 2010 及更早版本向 Exchange Online 迁移公共文件夹被阻止 | 有老旧公共文件夹的企业需单独规划 |

## 进入第4篇的条件

1. 内外部邮件收发稳定，连续观察期内无 P1 故障。
2. 大邮箱、共享邮箱、委派关系用户、管理层数据已 100% 核对。
3. 客户端配置未完成人数已清零。
4. 误投旧系统的邮件已全部补投，且旧系统连续 3 天无新邮件。
5. 邮件身份验证（SPF/DKIM/DMARC）认证与域对齐通过。
6. 邮件安全策略已生效，隔离区有责任人复核。
7. 迁移账号、条件访问临时例外、允许列表临时项已回收或有到期管理。
8. 迁移结果登记与验收签字完成。

> **推荐：** 第4篇（Office、Teams、文件）可以与本篇的**收尾工作并行**，但不建议与**切换窗口**同期进行。切换当天应避免同时推进其他变更，以便隔离故障来源。
