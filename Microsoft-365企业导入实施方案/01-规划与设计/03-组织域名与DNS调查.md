## 1.9 企业基本信息和办公地点调查

调查企业基本信息的目的，是确定租户区域、语言、时区、网络出口、支持时间和数据要求。

### 1.9.1 必须收集的字段

| 字段 | 填写说明 | 示例（虚构） |
|---|---|---|
| 企业正式名称 | 与合同、账单一致 | 示例科技有限公司 |
| 常用简称 | 用于显示和文档 | 示例科技 |
| 总部国家或地区 | 企业经营与需求背景，不等于租户Default Geography | 中国 |
| 拟选租户创建国家或地区 | 创建后不能直接更改，必须单独审批 | 待确认 |
| 预计服务数据位置 | 按Exchange、Teams、SharePoint等分别核对 | 待确认 |
| 办公地点 | 每个地点单独一行 | 上海、北京、新加坡 |
| 默认语言 | 管理和用户培训语言 | 简体中文 |
| 默认时区 | 会议和审计常用时区 | UTC+8 |
| 员工总数 | 包括正式和临时人员 | 180 |
| 预计上线人数 | 本期使用 Microsoft 365 的人数 | 150 |
| IT 支持时间 | 影响切换和服务台 | 工作日 09:00～18:00 |
| 行业监管要求 | 由法务/合规确认 | 待确认 |
| 项目负责人 | 对范围和进度负责 | 项目经理A |
| 业务决策人 | 对上线和回退作决定 | 业务负责人B |

### 1.9.2 多办公地点的额外调查

每个地点分别收集：

- 员工人数和高峰同时在线人数。
- 互联网运营商和线路带宽。
- 是否统一通过总部上网。
- 是否使用 VPN、代理、SSL 检查或防火墙白名单。
- 是否有会议室设备。
- 是否有现场 IT 支持人员。
- 与其他办公地点的网络连接方式。

> **验证点：** 企业人数、预计上线人数和许可证数量必须能相互解释。如果员工总数为 180，但只采购 100 个账号，需要明确剩余 80 人的身份和使用方式。

## 1.10 员工、部门和组织结构调查

用户清单是账号创建、许可证分配、邮件迁移、Teams 权限和离职交接的基础。

### 1.10.1 用户清单至少包含

| 字段 | 是否必填 | 用途 |
|---|---:|---|
| 员工唯一编号 | 是 | 防止同名员工混淆 |
| 中文姓名/显示名称 | 是 | 通讯录显示 |
| 英文名或拼音 | 按需 | 登录名和跨国协作 |
| 部门 | 是 | 分组和权限 |
| 职务 | 推荐 | 通讯录和管理 |
| 直属主管 | 推荐 | 审批和组织关系 |
| 办公地点 | 是 | 网络、语言和策略 |
| 在职状态 | 是 | 决定是否建账号 |
| 员工类型 | 是 | 正式、临时、外包、来宾 |
| 当前邮箱地址 | 有邮箱则必填 | 邮件迁移映射 |
| 计划登录名 | 是 | 创建账号 |
| 计划主邮箱地址 | 使用邮箱则必填 | Exchange 配置 |
| 所需服务 | 是 | Office、邮箱、Teams 等 |
| 是否为管理员 | 是 | 权限隔离 |
| 是否为重点保护对象 | 推荐 | 高管、财务、人事等 |

### 1.10.2 需要提前制定的命名规则

常见登录名形式包括：

- `firstname.lastname@example.com`
- `givenname@example.com`
- `employeeid@example.com`

命名时要处理：

- 同名员工。
- 姓名变更。
- 外籍员工。
- 较长姓名。
- 特殊字符。
- 账号是否允许重复利用。

> **推荐：** 登录名和主邮箱地址尽量保持一致，减少用户困惑；账号离职后不要立即分配给新员工。

### 1.10.3 组织结构不要只依赖“部门”字段

还需要明确：

- 谁是部门负责人。
- 谁负责批准 Teams 和文件权限。
- 哪些人跨部门工作。
- 哪些部门需要共享邮箱。
- 哪些人员是外部来宾而不是内部员工。
- 哪些账号属于系统或设备，不能按普通员工处理。

## 1.11 企业域名和 DNS 管理权限调查

企业域名用于登录名、邮箱地址和品牌展示。DNS 控制权决定项目能否验证域名、切换邮件和配置邮件身份验证。

### 1.11.1 域名调查表

| 字段 | 说明 |
|---|---|
| 域名 | 例如 `example.com` |
| 域名用途 | 主邮件域、品牌域、历史域、网站域 |
| 注册商 | 域名购买和续费机构 |
| DNS 托管商 | 实际维护解析记录的服务商 |
| 域名所有人 | 企业还是第三方 |
| 到期日期 | 防止迁移期间域名过期 |
| 管理账号保管人 | 谁可以登录 |
| 是否启用 MFA | 域名管理账号也应保护 |
| 当前 MX | 当前邮件接收位置 |
| 当前 SPF | 所有合法发信系统 |
| DKIM 状态 | 哪些系统已签名 |
| DMARC 状态 | 当前策略及报告地址 |
| 网站记录 | 防止误删网站解析 |
| 第三方发信系统 | CRM、工资单、营销平台等 |

### 1.11.2 调查阶段严禁做什么

- 不要修改 MX 记录。
- 不要删除现有 SPF 内容。
- 不要把整个 DNS 区域交给不明第三方。
- 不要假设域名注册商就是 DNS 托管商。
- 不要在未创建目标邮箱时把邮件切到 Microsoft 365。

微软建议企业使用自有域名，并明确提醒：在把 MX 指向 Microsoft 365 前，应先创建所有接收邮件的用户和邮箱，否则可能造成邮件中断。可参考 [向 Microsoft 365 添加自定义域](https://learn.microsoft.com/en-us/microsoft-365/admin/setup/add-domain?view=o365-worldwide)。

### 1.11.3 必须取得的权限

项目至少需要：

- 查看全部 DNS 记录的权限。
- 新增 TXT、CNAME、MX 等记录的权限。
- 修改和回退记录的权限。
- 导出现有记录或截图留档的能力。
- 域名和 DNS 服务商的应急支持渠道。

> **高风险：** 每个用于发信的域或子域只能发布一条 SPF 记录。多个合法发信源必须合并到这一条记录中；同时要计算嵌套 `include` 等机制产生的 DNS 查询次数，避免超过 SPF 规定的 10 次查询上限。不要为同一个域再创建第二条互相冲突的 SPF 记录。详细规则见 [Microsoft 365 SPF 配置说明](https://learn.microsoft.com/en-us/defender-office-365/email-authentication-spf-configure)。

### 1.11.4 邮件身份验证的规划和验收原则

SPF、DKIM 和 DMARC 不是“DNS 中有记录就算完成”。项目必须从外部收件系统取得测试邮件头，确认合法发信源的认证结果以及域对齐关系：

- SPF 不仅要显示 `spf=pass`，还要检查信封发件域（MAIL FROM）是否与用户可见的 From 域满足 DMARC 对齐。
- DKIM 不仅要显示 `dkim=pass`，还要检查签名中的 `d=` 域是否与用户可见的 From 域满足 DMARC 对齐。
- DMARC 应显示 `dmarc=pass`；这表示 SPF 或 DKIM 至少有一项通过并满足对齐，不能只看 SPF 和 DKIM 各自是否通过。
- Microsoft 365 自定义域所需的两个 DKIM CNAME 目标值必须从 Microsoft Defender 门户或 Exchange Online PowerShell 的 `Get-DkimSigningConfig` 输出中读取。2025年后新增域可能采用动态分区字符的新格式，不能根据示例地址手工拼接。

DMARC 建议采用渐进方式：先以 `p=none` 收集并分析报告，修复漏登记的合法发信源和对齐问题，再逐步提高到 `p=quarantine`，最终以 `p=reject` 为目标。必要时可以用 `pct` 分阶段扩大策略覆盖比例。项目必须为 `rua` 聚合报告设置专用邮箱或 Microsoft 365 组，并指定监看责任人、检查频率和异常升级流程，不能把报告长期投递给无人维护的个人邮箱。详细方法见 [Microsoft 365 DKIM 配置说明](https://learn.microsoft.com/en-us/defender-office-365/email-authentication-dkim-configure) 和 [Microsoft 365 DMARC 配置说明](https://learn.microsoft.com/en-us/defender-office-365/email-authentication-dmarc-configure)。
