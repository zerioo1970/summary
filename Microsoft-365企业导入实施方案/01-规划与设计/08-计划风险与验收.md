## 1.31 制定试点、分批上线和正式切换计划

### 1.31.1 为什么必须试点

试点用于验证真实环境，而不是证明管理员会操作后台。试点应发现：

- 账号和登录名冲突。
- MFA注册及手机问题。
- 邮件迁移速度和数据缺失。
- Outlook重新配置问题。
- Office宏和插件兼容问题。
- Teams音视频和网络问题。
- 外部共享及权限问题。
- 用户培训和服务台能力不足。

### 1.31.2 试点用户组成

建议包含不同类型，而不是只选 IT 人员：

- 1～2名管理员。
- 普通办公用户。
- 财务或使用复杂 Excel 的用户。
- 管理层或助理。
- 大邮箱用户。
- 使用共享邮箱和代理权限的用户。
- 移动办公用户。
- 分支机构或远程用户。
- Mac 用户（如有）。
- 需要与外部人员协作的用户。

试点规模取决于企业人数和复杂度。重点是覆盖场景，而不是追求固定百分比。

### 1.31.3 示例阶段计划

以下仅为中小型企业示例，不能直接当作承诺工期：

| 阶段 | 示例周期 | 主要输出 | 进入下一阶段条件 |
|---|---|---|---|
| 现状调查 | 第1～2周 | 调查表、风险表 | 关键数据已核实 |
| 方案与采购 | 第2～3周 | 目标方案、许可表 | 方案和预算批准 |
| 基础建设 | 第3～4周 | 租户、域名、管理员 | 基础安全通过检查 |
| 试点实施 | 第5～6周 | 试点结果和问题表 | 严重问题已关闭 |
| 分批迁移 | 第7～8周 | 批次迁移结果 | 每批通过验证 |
| 正式稳定 | 第9～10周 | 稳定期报告 | 验收条件满足 |

### 1.31.4 批次划分原则

- 同一部门可放在同一批次，便于业务协作。
- 关键部门不要全部安排在首批。
- 同时具有复杂宏、大邮箱和外部协作的用户，先充分试点。
- 每批规模不能超过服务台当天可支持的能力。
- 给管理层和高风险用户安排专人支持。

### 1.31.5 每个阶段都要有回退条件

例如：

- MFA 策略导致大量用户无法登录。
- 关键应用无法使用新版 Office。
- 外部邮件无法稳定收发。
- 邮件迁移完整性低于验收标准。
- Teams 会议质量不满足业务需要。

回退不是“出问题再想办法”，而是在上线前形成可以执行的书面计划。每个高风险变更的回退计划至少填写：

| 字段 | 填写要求 |
|---|---|
| 变更对象 | 例如 MX、条件访问、Office版本或迁移批次 |
| 触发阈值 | 什么错误、影响多少人、持续多久就必须回退 |
| 最晚决策时间 | 超过什么时间后继续操作会失去回退窗口 |
| 决策人 | 谁有权宣布暂停和回退 |
| 执行人 | 谁负责具体恢复操作 |
| 恢复步骤 | 按顺序写明恢复配置和数据的方法 |
| 增量数据处理 | 切换后新产生的邮件或文件如何保留、补回和去重 |
| 用户通知 | 通知对象、渠道、模板和发布时间 |
| 验证方法 | 如何证明旧服务或替代方式已经恢复 |
| 证据位置 | DNS截图、日志、导出文件和审批记录保存在哪里 |
| 再次上线条件 | 哪些问题修复并重新测试后才能继续 |

> **必做：** 回退计划必须作为第1篇正式交付物，由技术执行人和业务决策人共同审阅。只写“必要时恢复原配置”不算可执行的回退方案。

## 1.32 项目角色和职责分工

### 1.32.1 建议角色

| 角色 | 主要职责 |
|---|---|
| 项目发起人 | 批准目标、预算和重大范围变更 |
| 项目经理 | 计划、协调、风险、会议和进度 |
| Microsoft 365总管理员 | 租户、角色和跨服务协调 |
| 身份管理员 | 用户、组、AD同步、MFA和登录安全 |
| Exchange管理员 | 邮箱、迁移、邮件流和邮件安全 |
| Teams/SharePoint管理员 | 协作、会议、站点、文件和外部访问 |
| Office/终端管理员 | Office部署、设备和兼容性 |
| 网络管理员 | DNS、出口、防火墙、代理和Teams质量 |
| 安全/合规负责人 | 安全基线、保留、审计和数据要求 |
| 人力资源 | 员工清单和入转离触发 |
| 业务负责人 | 需求、试点用户和业务验收 |
| 服务台 | 用户通知、培训和一线故障处理 |
| 采购/法务 | 合同、许可证、合规和供应商管理 |
| 实施供应商 | 按约定交付、记录和知识转移 |

### 1.32.2 RACI 是什么

- **R（Responsible）：** 实际执行工作的人。
- **A（Accountable）：** 对结果最终负责和批准的人，每项最好只有一个。
- **C（Consulted）：** 执行前需要征求意见的人。
- **I（Informed）：** 需要获知结果的人。

### 1.32.3 简化 RACI 示例

| 工作项 | 项目经理 | M365管理员 | 网络管理员 | 业务负责人 | 安全负责人 |
|---|---|---|---|---|---|
| 租户选型 | R | C | I | A | C |
| 域名和DNS切换 | I | R | A/R | I | C |
| MFA策略 | I | R | I | C | A |
| 邮件迁移 | A | R | C | C | I |
| Office兼容测试 | A | R | I | R | I |
| 正式上线决定 | R | C | C | A | C |

> **必做：** 每项高风险操作必须有执行人、批准人和回退决定人。不能只写“IT负责”。

## 1.33 项目成功标准和验收标准

“系统能登录”不是完整的成功标准。验收必须可测量、有证据、有责任人。

### 1.33.1 建议的验收指标

| 范围 | 验收标准示例 | 证据 |
|---|---|---|
| 账号 | 本期用户全部按批准清单创建，无重复主地址 | 用户导出清单 |
| MFA | 范围内用户完成注册；管理员保护已验证 | 注册报告、测试记录 |
| 管理权限 | 无未经批准的全局管理员；紧急账号已测试 | 角色清单、演练记录 |
| 邮件迁移 | 所有批准邮箱完成迁移，失败项有处理结论 | 迁移报告 |
| 邮件收发 | 内部、外部、共享邮箱和会议室测试通过 | 测试用例 |
| DNS与邮件身份验证 | MX、Autodiscover达到本期目标；所有合法发信源完成SPF/DKIM实发测试，DMARC认证及域对齐通过；策略阶段、报告责任人和例外有记录 | DNS查询、外部测试邮件头、DMARC报告和批准记录 |
| Office | 目标设备完成安装激活；关键宏插件通过测试 | 设备和兼容表 |
| Teams | 登录、聊天、会议、录制及目标外部场景通过 | Teams测试记录 |
| 文件 | 权限、同步、版本和恢复测试通过 | 测试记录 |
| 安全 | 最低安全基线全部完成或有批准的例外 | 安全检查表 |
| 运维 | 入转离、巡检、恢复和支持流程可执行 | 流程文档和演练 |
| 培训 | 管理员及员工完成规定培训 | 签到和反馈 |

### 1.33.2 指标必须补充阈值

例如不要只写“邮件迁移成功”，应在项目验收表中填写以下字段：

| 字段 | 示例写法（需要企业自行确认） |
|---|---|
| 目标对象数 | 本批共 `___` 个用户/邮箱/设备 |
| 成功率 | 不低于 `___%`，并说明分母和统计时间 |
| 允许例外数 | 最多 `___` 项，每项必须有负责人和截止日期 |
| 抽查方式 | 抽查 `___` 个对象，覆盖大邮箱、共享邮箱和重点用户 |
| P1/P2条件 | 上线前 P1 必须为 `0`；P2 允许数量为 `___` |
| 稳定观察期 | 连续 `___` 个工作日无新的严重故障 |
| 签字人 | 业务负责人、IT负责人和安全负责人 |
| 证据位置 | 报告、日志、截图和用户确认保存路径 |

阈值应在试点前批准，不能在结果出来后为了通过验收而临时降低。

### 1.33.3 建议的故障等级

| 等级 | 定义示例 | 上线影响 |
|---|---|---|
| P1 严重 | 大量用户无法登录或全公司邮件中断 | 停止切换并评估回退 |
| P2 高 | 一个部门或关键人员无法工作 | 优先修复，决定是否暂停下一批 |
| P3 中 | 有替代办法的功能异常 | 记录并限期修复 |
| P4 低 | 使用问题、界面或优化建议 | 纳入知识库和改进计划 |

## 1.34 项目风险、依赖和限制条件登记

### 1.34.1 风险与问题的区别

- **风险：** 未来可能发生，例如“DNS账号可能无法及时取得”。
- **问题：** 已经发生，例如“目前确认没有人能登录DNS后台”。
- **依赖：** 项目必须等待的条件，例如“必须先取得域名所有权验证”。
- **限制：** 无法随意改变的边界，例如“正式切换只能在周末进行”。

### 1.34.2 风险登记字段

| 字段 | 说明 |
|---|---|
| 编号 | 唯一编号 |
| 风险描述 | 可能发生什么 |
| 影响 | 对业务、时间、成本或安全的影响 |
| 概率 | 高、中、低 |
| 严重度 | 高、中、低 |
| 应对措施 | 如何降低概率或影响 |
| 触发条件 | 什么时候认为风险已发生 |
| 应急方案 | 发生后如何处理 |
| 负责人 | 谁持续跟进 |
| 截止日期 | 何时必须解决 |
| 状态 | 开放、处理中、关闭、接受 |

### 1.34.3 常见风险示例

| 风险 | 影响 | 预防措施 |
|---|---|---|
| 选错全球版/世纪互联版 | 需要重新采购或迁移 | 先完成地区、功能和合规评审 |
| 域名或DNS权限不在企业手中 | 无法验证域名或切换邮件 | 提前完成账号接管和权限测试 |
| 本地AD属性混乱 | 重复账号和同步失败 | 同步前清理并小范围试点 |
| 旧式客户端不支持现代认证 | MFA后无法登录 | 提前盘点并升级或替换 |
| 邮箱数据量估计过低 | 切换窗口超时 | 导出真实容量并进行试迁移 |
| Excel宏或插件不兼容 | 关键业务中断 | 代表性电脑完整测试 |
| Teams网络质量差 | 会议卡顿和掉线 | 分地点测试并优化网络 |
| 外部共享过度开放 | 数据泄露 | 最小权限、审批和定期复核 |
| 唯一全局管理员不可用 | 无法管理租户 | 建立紧急访问账号和演练 |
| 许可证能力理解错误 | 功能不可用或违规使用 | 书面核对服务说明和合同 |
| 服务台能力不足 | 上线当天问题积压 | 控制批次规模并提前培训 |
| 没有回退方案 | 故障时无法恢复 | 每个高风险变更写明回退步骤 |

### 1.34.4 风险处理原则

- 高概率、高影响风险必须在试点前有明确措施。
- 无法消除的风险要由有权负责人正式接受。
- “供应商说没问题”不是风险关闭证据。
- 每周项目会议复核开放风险。
- 正式切换前重新评估所有高风险项。

### 1.35.4 进入第2篇的条件

满足以下条件后，再开始建立或修改正式租户：

1. 租户类型已有正式结论。
2. 企业确认自己掌握租户、域名、DNS和合同控制权。
3. 目标身份模式和管理员责任已经明确。
4. 许可证能力与数量已经过初步核对。
5. 试点和回退原则已经批准。
6. 未解决的高风险项目有明确负责人和截止日期。

如果以上条件尚未全部满足，可以创建隔离的测试环境学习，但不应切换正式企业域名和生产邮件。
