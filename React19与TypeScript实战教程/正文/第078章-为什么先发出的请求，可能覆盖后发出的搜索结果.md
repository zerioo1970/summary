# 第 78 章：为什么先发出的请求，可能覆盖后发出的搜索结果？

前置：[第 77 章：如何等用户停止输入后再发起搜索？](第077章-如何等用户停止输入后再发起搜索.md)

## 一、本章要解决的问题

防抖减少了请求，但并不能保证只有一个请求。用户输入 `t`，停顿一下，再接着输入 `ype`，就会先后发出 `q=t` 和 `q=type` 两个请求。

网络请求的返回顺序没有保证。如果 `t` 的请求比 `type` 的晚回来，页面上最后显示的会是 `t` 的结果：输入框里是 `type`，下面却列出了三篇文章。

本章不修改代码，而是故意去掉 `ignore` 的检查，重现这个问题，弄清搜索 Effect 中的清理函数是怎样避免它的。

## 二、必要原理

### 请求的返回顺序没有保证

一个请求要多久才回来，取决于网络和服务器的处理速度，和发出的先后无关。为了方便重现，练习服务的搜索接口故意让两个字以内的关键词等 1.5 秒才响应，更长的关键词只等 0.3 秒。所以：

| 时间 | 发生的事 |
| --- | --- |
| 第 0 秒 | 输入 `t` |
| 约 0.5 秒 | 防抖结束，发出 `q=t` 的请求，要 1.5 秒 |
| 约 0.7 秒 | 继续输入 `ype` |
| 约 1.2 秒 | 防抖结束，发出 `q=type` 的请求，要 0.3 秒 |
| 约 1.5 秒 | `type` 的结果先回来，显示 1 篇 |
| 约 2 秒 | `t` 的结果后回来，又把列表换成了 3 篇 |

这类问题叫**竞态**：几件同时进行的事，最后的结果取决于谁先完成。

### 每次搜索都有自己的 ignore

搜索的 Effect 每执行一次，就创建一个新的 `ignore` 变量，它属于这一次搜索。关键词从 `t` 变成 `type` 时，React 先执行 `t` 那一次的清理函数，把 **`t` 的** `ignore` 设为 `true`，再为 `type` 执行 Effect，创建新的 `ignore`。

`t` 的请求晚回来时，检查的是它自己的 `ignore`，已经是 `true`，结果被丢弃。页面上只会显示最后一次 Effect 的结果。

第 75 章为了应对 StrictMode 写下的 `ignore`，同时也解决了竞态问题：它们本质上是同一件事，即“已经被清理的 Effect，不能再更新页面”。

## 三、动手实现

保持开发服务器和练习服务都在运行（准备篇二）。本章对代码的修改都是临时的，做完后恢复为第 77 章的代码。

### 第 1 步：去掉成功时的 ignore 检查

在 `src/pages/SearchPage.tsx` 的搜索 Effect 中，把：

```tsx
        if (!ignore) {
          setSearchState({ status: 'success', items });
        }
```

临时改为：

```tsx
        setSearchState({ status: 'success', items });
```

### 第 2 步：重现竞态

打开 Network（网络）面板，在搜索框中输入 `t`，等大约 0.7 秒，看到 `q=t` 的请求出现后，马上输入 `ype`。

先短暂显示 1 篇“TypeScript 类型检查”，大约半秒后又变成了 3 篇文章。在 Network 中可以看到，`q=t` 的请求比 `q=type` 发得早，却结束得晚。

### 第 3 步：恢复检查后再试

把第 1 步的修改恢复，用同样的方式输入。这次 `t` 的请求仍然晚回来，但页面一直只显示 1 篇。

## 四、运行与检查

1. 去掉检查后，按第三节第 2 步输入，最终显示 3 篇文章，和输入框中的 `type` 不符。
2. 恢复检查后，同样的输入，最终只显示“TypeScript 类型检查”。
3. 两种情况下，Network 中的请求都是 2 个，`q=t` 都比 `q=type` 晚结束。区别只在于晚到的结果有没有被使用。

最后运行检查，应没有错误：

```powershell
npm.cmd run check
```

**小练习**：如果只保留成功时的 `ignore` 检查、去掉失败时的检查，旧请求失败而新请求成功时，页面最后会显示什么？先想一想，再说说为什么两处都要检查。

## 五、常见错误

| 现象 | 原因 | 怎么改 |
| --- | --- | --- |
| 偶尔显示的结果和输入框中的关键词对不上 | 晚回来的旧请求覆盖了新结果 | 在 Effect 的清理函数中标记旧请求，结果回来后先检查 |
| 以为防抖就能避免这个问题 | 防抖只减少请求数量，用户停顿一下就会有多个请求 | 防抖和清理两者都要有 |
| 本机测试时从来没遇到，上线后才出现 | 本机的网络很快，请求几乎按顺序返回 | 用练习服务的慢速关键词，或 `?delay=` 参数主动测试 |
| 把 `ignore` 放到组件外面或用一个 state 记录 | 所有搜索共用一个标记，没法区分新旧请求 | 每次执行 Effect 都创建自己的 `ignore` |
| 学完本章后，页面一直报错、一直显示空数据或加载很慢 | 步骤中临时加在请求地址上的 `?mode=`、`?fail=`、`?delay=`、`?cors=` 等参数忘了删 | 运行 `git diff` 查看本章改动，删掉地址中的临时参数 |
