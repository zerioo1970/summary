# 第 7 章：写错代码时，如何让检查命令提前发现问题？

前置：[第 6 章：页面一片空白时，如何找到第一条有用的错误信息？](第006章-页面一片空白时，如何找到第一条有用的错误信息.md)

## 一、本章要解决的问题

第 3 章和第 6 章都遇到过：代码有错，开发服务器照样显示页面，只有等到页面空白或者内容不对时才发现。如果能在保存之后、打开浏览器之前就发现问题，排查会轻松很多。

本章安装代码检查工具 oxlint，并把类型检查和代码检查合成一个命令 `npm.cmd run check`。完成后，运行这一个命令，就能同时发现类型错误和容易出问题的写法。从本章起，每章结束都运行它。

## 二、必要原理

### 两种检查，各管一类问题

- **类型检查（TypeScript）**：检查数据用得对不对，例如属性名拼错、把数字给了需要文字的地方。命令是准备篇一建立的 `npm.cmd run typecheck`。
- **代码检查（oxlint）**：检查写法上的隐患，例如忘了删除的调试语句、条件永远成立的判断。后面学到 React 的 Hook 时，它还能检查 Hook 的使用规则，这类错误类型检查发现不了。

这类工具在英文中叫 linter，运行它的过程叫 lint。实际项目中常用的是 ESLint。本教程选择 oxlint，因为它配置简单、运行速度快，而且不依赖 TypeScript 7 尚未提供的编程接口，可以直接用于本项目。

### 开发服务器为什么不检查

Vite 开发服务器为了快，只负责把代码转换成浏览器能运行的形式，不做类型检查和代码检查。所以页面能显示，不代表代码没有问题。检查需要单独运行。以后用 `npm.cmd run build` 构建正式版本时（第 137 章），也会先做类型检查。

### VS Code 能不能直接显示错误

能，但要分两种情况看。

**类型错误：VS Code 自己就能显示。** VS Code 自带 TypeScript 支持，打开 `.tsx` 文件后，类型写错、属性名拼错、少传了数据这类问题会直接画红色波浪线。鼠标停在波浪线上可以看到原因；按 `Ctrl+Shift+M` 打开“问题”面板，可以看到所有错误。这和 `typecheck` 查的是同一类问题。

**oxlint 的规则：要装 Oxc 插件才能显示。** `no-debugger`、后面的 Hook 规则这些是 oxlint 的规则，VS Code 本身不认识。装上 oxlint 官方的 VS Code 插件 **Oxc** 后，违反规则的代码也会画波浪线，并出现在“问题”面板里。

要注意的是，**插件本身不做检查，真正检查的是项目里的 oxlint**。插件只是在你写代码时调用项目中安装的 oxlint，再把结果画在编辑器里。所以插件离不开 oxlint：项目里没装 oxlint，装了插件也不会有任何 oxlint 提示。两者不是二选一，而是这样配合：

| | 只装 oxlint | oxlint + Oxc 插件 |
| --- | --- | --- |
| 能不能查出问题 | 能 | 能，查出的问题完全一样 |
| 什么时候看到 | 运行 `npm.cmd run check` 时，在终端里看到 | 写代码时就在编辑器里看到 |
| 换一台电脑、换一个编辑器 | 一条命令就能检查 | 要再装一次插件 |

本教程的做法是：

1. **oxlint 必须装**。以 `npm.cmd run check` 的结果作为“是否通过”的标准，它不依赖哪个编辑器，以后构建时也能自动运行。
2. **插件可选**。装了以后错误发现得更早，写代码更顺手，但查出来的问题和命令一样。

类型错误也是同样的道理：VS Code 的红色波浪线是提前提示，最后还是以 `check` 里的类型检查结果为准。

### 配置文件 .oxlintrc.json

oxlint 默认开启“正确性”类规则，专门找几乎肯定是错误的写法。但它检查 React 的插件默认是关闭的，需要在项目根目录的 `.oxlintrc.json` 中开启：

```json
{
  "plugins": ["eslint", "typescript", "unicorn", "oxc", "react"],
  "rules": {
    "react/rules-of-hooks": "error",
    "react/exhaustive-deps": "error"
  }
}
```

- `plugins` 列出要启用的检查插件。前四个是 oxlint 默认启用的，最后的 `react` 是新加的。在这里写了 `plugins`，就会替换默认列表，所以默认的四个也要写上。
- `rules` 把两条与 Hook 有关的规则设为“错误”。现在还用不到它们，第 26 章学习 state 后就会派上用场。

## 三、动手实现

### 第 1 步：安装 oxlint

在项目根目录的终端中运行（开发服务器不需要停止）：

```powershell
npm.cmd install --save-dev --save-exact oxlint@1.89.0
```

- `--save-dev`：作为开发工具安装，写入 `devDependencies`。
- `--save-exact`：在 `package.json` 中记录精确版本 `1.89.0`，不加 `^`。

安装完成后，`package.json` 的 `devDependencies` 中多了一行 `"oxlint": "1.89.0"`。

### 第 2 步：新建配置文件

在项目根目录（与 `package.json` 同一个文件夹）新建 `.oxlintrc.json`，内容就是第二节中的配置。

### 第 3 步：添加检查命令

打开 `package.json`，在 `scripts` 中 `typecheck` 那一行的下面加入两行：

```json
    "typecheck": "tsc --noEmit",
    "lint": "oxlint src",
    "check": "npm run typecheck && npm run lint",
```

- `lint`：用 oxlint 检查 `src` 文件夹中的代码。练习服务的代码不需要你维护，所以不检查它。
- `check`：先运行类型检查，通过后再运行代码检查。`&&` 表示前一个命令成功才执行后一个。

### 第 4 步：确认当前代码没有问题

```powershell
npm.cmd run check
```

先看到类型检查运行，接着 oxlint 输出类似 `Found 0 warnings and 0 errors.` 的结果，表示没有发现问题。

### 第 5 步：让类型检查发现错误

打开 `src/App.tsx`，把 `profile` 中的身份临时改成一个数字：

```tsx
    role: 18,
```

保存后运行 `npm.cmd run check`，类型检查报错，命令在这里停止，不再运行 oxlint：

```text
src/App.tsx:13:5 - error TS2322: Type 'number' is not assignable to type 'string'.
```

意思是：第 13 行第 5 列，“`number` 类型不能赋给 `string` 类型”。`Profile` 规定 `role` 是字符串，这里却写了数字。改回 `role: '前端开发学习者',`。

### 第 6 步：让代码检查发现问题

在 `App` 函数中、`return` 的上一行临时加入：

```tsx
  debugger;
```

`debugger` 语句会让打开了开发者工具的浏览器在这里暂停，是调试时临时加的，提交代码前应该删除。

**先关闭浏览器的开发者工具再保存**（第 6 章打开过它，按 F12 可以关闭）。如果开发者工具开着，保存后页面会停在这一行，变成灰色，顶部显示“已在调试程序中暂停”，页面上的按钮也点不动。这不是项目坏了，按 F8 或点击页面顶部的继续按钮（▶）就能继续运行。

保存后运行 `npm.cmd run check`，这次类型检查通过，oxlint 报告了问题。输出大致如下：

```text
  × eslint(no-debugger): `debugger` statement is not allowed
    ╭─[src/App.tsx:17:3]
 16 │
 17 │   debugger;
    ·   ─────────
 18 │   return (
    ╰────
Found 0 warnings and 1 error.
```

第一行是规则名和说明，`src/App.tsx:17:3` 是位置（第 17 行第 3 列），下面标出了出问题的代码。先不要删这一行，第 7 步还要用它。

### 第 7 步（可选）：在 VS Code 中实时显示 oxlint 的结果

1. 在 VS Code 左侧点击“扩展”图标（或按 `Ctrl+Shift+X`），搜索 **Oxc**。
2. 找到发布者为 oxc 的插件，确认它的标识符是 `oxc.oxc-vscode`，点击“安装”。也可以按 `Ctrl+P`，输入 `ext install oxc.oxc-vscode` 后回车。
3. 回到 `src/App.tsx`。第 6 步加的 `debugger;` 下面出现波浪线，鼠标停在上面，可以看到和命令行相同的 `no-debugger` 提示。
4. 按 `Ctrl+Shift+M` 打开“问题”面板，这条问题也列在里面。

确认看到提示后，删掉这一行 `debugger;`，波浪线随之消失。

如果装好插件却没有出现波浪线，通常是因为插件启动时项目里还没有 oxlint（例如先装了插件，后运行第 1 步）。按 `Ctrl+Shift+P`，运行 **Oxc: Restart oxlint Server** 重启插件的检查服务即可。

不装插件也完全不影响后面的学习，每章结束时运行 `npm.cmd run check` 就行。

## 四、运行与检查

保持开发服务器运行（`npm.cmd run dev`）。

1. 按第三节第 5、6 步操作时，`check` 分别报告了类型错误和 `no-debugger` 问题，并指出文件和行号。
2. 两处都恢复后，`npm.cmd run check` 不报告任何错误。
3. 页面与第 5 章相同，本章没有改变页面内容。
4. 如果做了第 7 步：`debugger;` 存在时，编辑器中有波浪线，“问题”面板中有 `no-debugger`；删除后两处都消失。

从本章起，每章结束时运行一次：

```powershell
npm.cmd run check
```

没有错误再用 Git 提交（准备篇三）。

**小练习**：在 `return` 上一行写 `profile.role = profile.role;`（把一个值赋给它自己，这一行什么也没做），运行 `check`，看看 oxlint 报告了哪条规则、说了什么。读懂后删除这一行。

## 五、常见错误

| 现象 | 原因 | 怎么改 |
| --- | --- | --- |
| 提示 `'oxlint' 不是内部或外部命令` | 没有安装成功，或在别的文件夹中运行 | 在项目根目录重新运行第三节第 1 步 |
| `check` 只运行了类型检查就结束了 | 类型检查有错误，`&&` 后面的 `lint` 不会运行 | 先修好类型错误 |
| oxlint 报告了 `server` 文件夹中的问题 | `lint` 命令中漏写了 `src` | 写成 `oxlint src` |
| oxlint 提示配置文件格式错误 | `.oxlintrc.json` 中有多余逗号或中文引号 | 对照第二节逐字检查 |
| 编辑器中看到红线，`check` 却通过了 | 文件没有保存，命令检查的是磁盘上的文件 | 保存所有文件后再运行 |
| 保存后页面变灰，显示“已在调试程序中暂停” | 开发者工具开着，浏览器在 `debugger;` 处暂停了 | 按 F8 继续；做这一章时先按 F12 关闭开发者工具 |
| 装了 Oxc 插件，`debugger;` 下面却没有波浪线 | 插件启动时项目里还没有 oxlint，或项目没装 oxlint | 确认第 1 步已完成，再按 `Ctrl+Shift+P` 运行 Oxc: Restart oxlint Server |
| 只装了插件，没有运行第 1 步 | 插件不自带 oxlint，它调用的是项目里的 oxlint | 运行第三节第 1 步 |

## 七、本章改动小结

新增 `.oxlintrc.json`；修改 `package.json`（新增 oxlint 依赖，新增 `lint`、`check` 两个命令）；`package-lock.json` 由安装命令自动更新。`src` 中的代码没有变化。VS Code 的 Oxc 插件装在编辑器里，不属于项目文件，装不装都不影响上面的改动。
